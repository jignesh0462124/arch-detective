@292
This project used an engineering development method. The starting point was a practical problem: after a scan, a developer needs to know what was found, where it was found and whether the available evidence supports taking action. The research therefore considered the whole review process, from accepting a project to opening the saved report. A successful upload alone would not answer the problem, and a long findings list would be of limited use if the developer could not trace entries back to the source.

The work was divided into requirements, design, implementation and evaluation. The design stage identified the data that must survive between steps: a scan reference, its workspace, the status of the analysis and the locations associated with saved findings. Implementation then used this common structure for the Workbench, Findings and Reports. Evaluation considered functional behaviour separately from detection quality. The former can be demonstrated with an observed workflow; the latter requires a sample with independently established labels.
@293
Figure 3.1 summarises the sequence. It brings the developer's actions and the internal processing steps together, without treating them as interchangeable. Archive acceptance means that the system has taken responsibility for a request. It does not mean that analysis has finished. Likewise, saving a finding makes it available for review; it does not establish that a defect can be reproduced at runtime. These distinctions determine what the later screenshots and evaluation tables can support.
@294
The review process also provides a way to investigate disagreements. A reviewer can compare the finding description with the recorded path, the line or excerpt, the detection origin and the suggested remedy. If the excerpt is missing, or if it does not justify the description, the right outcome is to retain that uncertainty. It would be misleading to replace a limited source observation with a more definite conclusion simply because the system can generate a longer explanation.
@298
The functional requirements follow the order in which a developer uses the application. The user signs in, selects a permitted workspace, starts an audit, follows its progress and reviews the saved findings. The review should support a source lookup, severity and status filters, and a report that can be reopened after leaving the Workbench. A valid request must return a stable scan reference so that navigation or a page reload does not create a second audit by itself.
@299
The non-functional requirements specify what should happen when the normal path cannot complete. Uploads and previews have defined bounds; access must be checked in the workspace that owns the scan; and a file reference should indicate when the corresponding preview is unavailable. Interface messages must distinguish an in-progress scan, a failed scan and a completed scan with no findings returned. Treating these states as equivalent would make an incomplete review look like a clean result.
@300
Each requirement can be checked against a specific observation rather than a general impression of the interface. For example, a persistence check should reopen the same scan after navigation and confirm its reference. A reporting check should compare the exported report with the saved audit. An authorisation check is different: it requires an account without the necessary access and an explicit denial. A screenshot taken with the owner account is useful for demonstrating the interface but cannot replace that negative test.
@302
Input selection serves two purposes. Authorised application projects show whether a realistic project structure can be uploaded and reviewed. Controlled fixtures support narrower questions about detection or error handling. A useful detection fixture includes a known weakness, while a corrected counterpart and a similar benign case show whether the detector distinguishes the underlying condition from a familiar pattern. The fixture label needs to come from manual inspection or a reliable published description, not the scanner being evaluated.
@303
For a comparative evaluation, each input should have a short record describing its origin, version, permission to use it, and expected findings. An archive checksum identifies the exact input, while a file inventory records what is present. A label should refer to a weakness category and a location or relevant code region. The reviewer should note whether the label was established from source inspection alone, supported by a safe test or left uncertain. This record makes it possible to tell a change in detector behaviour from a change in the input itself.
@304
The application captures used in this thesis come from project workspaces and demonstration inputs. They show how saved findings are presented. A complete list of independently labelled weaknesses, clean controls and input checksums was not available for those captures. They are therefore treated as workflow evidence and case examples, not as a detection benchmark. Section 6.2 explains the effect of this limitation on the results.
@305
Only inputs that the project team is permitted to inspect should be included in a repeatable collection. Where possible, a small synthetic fixture should stand in for a private repository or a file containing personal data. The useful property to retain is the code structure relevant to the test. Retaining unrelated account information or real credentials would not improve the measurement and would introduce a new security concern.
@307
Ingestion prepares an upload for inspection without running the submitted program. The archive must be accepted by the input validation rules before its entries are considered. Path and size checks help prevent extraction outside the intended directory or an unexpectedly large expansion. The file-selection policy then excludes unsupported, generated or otherwise out-of-scope material for the relevant audit type. The important boundary is between files present in the upload and files available to a particular analysis stage.
@308
The source preview and the scanner's analysis input serve different jobs. The preview supports human review; the analysis selection determines where a detector can look. A preview may be redacted, shortened or unavailable, and a file listed in the Workbench is not evidence that every analysis stage examined it. Coverage should therefore identify the relevant stage and report known exclusions. The number of preview entries cannot stand in for the number of files examined by the scanner.
@309
Source coordinates should be preserved when enough evidence is available. For a line-based detector, the useful record is the path together with the line or range from the original package. A location that could not be tied to the package should be described as unavailable. Masking or bounding a preview limits what can be displayed, but it does not make it acceptable to invent a location or present a manufactured excerpt. This is particularly important for minified files and snippets whose starting line is uncertain.
@311
Static scanning draws on rules or specialist checks appropriate to the configured profile. The outputs of these checks are not necessarily shaped alike: two tools may use different severity labels, and one may report a code line while another reports a package or configuration item. Normalisation translates the available details into a common finding record so that evidence from different origins can be presented together. It should preserve the origin and mark absent values as absent.
@312
Duplicate handling is part of this process because two outputs can refer to the same underlying issue. Matching needs a stable basis such as rule or weakness identity, file or package location and relevant evidence. A title is a useful description but is not a reliable identity. Two independent instances can share a title, and a later edit may move a finding to another line. For a comparison across releases, a changed line should lead to review of the source context rather than automatic closure of the earlier issue.
@313
A detector's failure or omission must remain visible after normalisation. An empty list with a successful status means that the relevant stage returned no records. An empty list after a stage was disabled, skipped or interrupted says something different about coverage. The evaluation therefore retains execution status alongside counts. This makes it possible to investigate why a result is missing without assuming that an unavailable detector examined the project.
@315
Model assistance is introduced after the evidence boundary has been established. The task for the model is to explain or help remedy a particular finding, using a limited set of authorised context. The caller supplies the selected evidence and asks the model to state its assumptions. Project files and retrieved material are treated as inputs to interpret, not as instructions that can alter the review objective or grant permission to carry out an action.
@316
When retrieval is enabled, an explanation may draw on relevant references in addition to the source excerpt. A useful experiment would record the retrieval mode, the corpus version and the references returned for each case. A reviewer can then check whether the cited passage actually supports the proposed mapping or advice. A reference such as a weakness description supplies background, but cannot show that the same condition is reachable in the submitted project.
@317
The model's output is kept separate from recorded source evidence. In a case where the available snippet shows a risky operation but no untrusted input, the output should distinguish the observed operation from the condition that would make it dangerous. If the service fails, has no usable context or ends before finishing, the review must say so. An incomplete suggestion is not equivalent to a finished remedy and should not be scored as one.
@319
Scoring answers a different question from weakness classification. A weakness identifier describes the kind of issue. A CVSS score, where supported, describes severity under the assumptions used to calculate it. A control mapping identifies a requirement that may be relevant to review. Triage records the team's decision about the issue. Combining these into one status would hide important distinctions: a severe candidate may remain unverified, and a relevant control does not by itself establish non-compliance.
@320
Interpretation should start with the evidence and retain the assumptions behind any score or mapping. If a score is unavailable, absence must not be displayed as a score of zero. If the evidence does not justify a vector or control, the brief should state what needs checking. A reviewer who disagrees with a mapping should be able to point to the missing condition or inaccurate reference rather than having to reject the entire scan record.
@321
At the report level, any total or percentage needs a clear denominator and a statement of coverage. For example, the number of assessed controls is not the same as the number of requirements in a framework. A source-based application scan cannot observe all organisational controls. The method therefore uses framework signals as review aids rather than treating them as certification or a substitute for a separate compliance assessment.
@323
Remediation begins with the reason for the finding. The first question is whether the available evidence establishes the problem described. Written steps can then give the smallest useful change and explain what it should preserve. Where a code example is available, it belongs in a separate read-only presentation. The developer should be able to compare it with recorded evidence without mistaking the suggestion for a change already made to the project.
@324
Verification should be tied to project behaviour. A reviewer can ask which input or code path is affected, how normal behaviour is preserved, and whether an appropriate test or a subsequent audit supports the proposed change. Passing a project test, opening a pull request and no longer observing a finding in a later scan represent distinct outcomes. None should silently overwrite the recorded triage decision. A comparison is only useful if both scans had a reasonable opportunity to examine the same issue.
@325
The report is generated from saved results. Its role is to make the evidence, scope and recommendations readable outside the Workbench, without performing a new scan. A report parity check should compare finding counts, paths, available scores and remediation with the corresponding saved audit. It should also distinguish deliberate redaction or an unavailable preview from a rendering problem. Private Advisor messages are not required to explain the saved findings and are not part of this comparison.
@327
The evaluation design separates functional tests, detection assessment, performance measurements and access-control checks. Functional checks cover transitions such as upload acceptance, progress and reopening saved results. Detection assessment requires independent labels. Performance measurements require timestamps for clearly defined events under a recorded configuration. Authorisation checks need both allowed and denied cases. A pass in one group does not imply a pass in another.
@328
A repeatable run record should state the application revision, profile, input identifier, enabled tools and whether any stage was skipped. For comparisons, the input set, matching rules and reporting scope should be fixed before reviewing aggregate results. If a tool fails or a sample is unsupported, the reason belongs in the results. Excluding it without explanation can make both coverage and runtime appear better than they actually were.
@329
The results chapter applies this design to the evidence available. It describes completed demonstrations and uses logged regression tests when their scope is documented. It keeps expected outcomes separate when an observation was not retained. Controlled detection comparisons and repeatable timing experiments are described as follow-up measurements where the required records are missing, rather than being inferred from screenshots or isolated examples.

The planned test sequence has two checkpoints. The first establishes whether the audit was usable: it records acceptance, any exclusions, which stages completed and whether the result could be reopened. The second concerns interpretation. It asks whether a reviewer can reproduce a location, identify the source of the recommendation and distinguish a finding that needs review from a verified defect. A recording of the second checkpoint without the first could conceal missing coverage; the first without the second could show a completed job whose output is difficult to act on.

Changes to an input should be evaluated against both checkpoints. Consider an independently labelled vulnerable fixture and a revised copy. If the original is reported but the revised copy is outside the analysis scope, disappearance of the finding is inconclusive. If both auditable regions are covered, the comparison can be examined more closely. A precise decision also checks whether the reported location moved or whether a previous duplicate is now represented by a different finding. This procedure avoids treating every change in count as a source-code improvement.
@331
Detection measurements begin with a matching decision. A reported item should match a labelled issue only when the weakness category and relevant location or code region refer to the same underlying condition. A written matching rule is especially important when tools report at different levels of detail. The evaluation unit should be fixed before counts are calculated, so that one labelled weakness cannot accidentally be counted several times.
@332
A true positive (TP) is a reported item that matches a labelled weakness under that rule. In a combined system, a group of duplicate reports should yield one match rather than one match per contributing tool. The contributing origins can still be recorded for later analysis.
@333
A false positive (FP) is a reported candidate that is rejected on the agreed evidence, including a finding raised on an independently checked benign case. An item should not be called false simply because the initial label set missed it. A potentially valid but unresolved item should be reviewed or kept separate from the measured set.
@334
A false negative (FN) is a labelled weakness with no matching report. If analysis never covered the file or package in question, the coverage restriction should be recorded as well. The distinction matters because adding a rule will not address a weakness in code that the scan never examines.
@335
Precision describes how many of the reported and adjudicated results are valid. Recall describes how many of the labelled issues were found. A tool can raise its apparent recall by reporting more candidates, at the cost of creating more review work. The two measures are therefore reported together, or left unreported where the required counts are not available.
@336
The F1 score combines precision and recall through their harmonic mean. It is a compact summary but does not reveal the distribution of missed weaknesses across languages or categories. The underlying counts and the scope of the input set remain necessary for interpretation. The formulas used in this thesis are given below.
@340
An undefined denominator is reported as such. For example, when a tool returns no adjudicated predictions, a precision value should not be guessed. When a group contains no labelled weaknesses, it cannot establish recall. The method also records how unresolved candidates are handled. Applying the same rule to each tool matters more than producing a complete-looking metric table.
@341
Time and coverage measurements accompany the detection metrics where records allow. Time to first visible result, analysis duration and elapsed time from submission to persistence are different measurements. A performance report should identify which one is used and whether queueing or model delays are included. The same record should state how many eligible files were examined so that a fast run with reduced coverage cannot be mistaken for an equivalent run.

Coverage can be reported at more than one level when the inventory exists. A file-level statement records how many eligible files a stage examined. A category-level statement records which classes of issue or policy checks that stage was intended to assess. The first does not answer the second: a scanner can examine an entire eligible file set and still have no rule for a particular weakness. A negative result therefore needs both the analysis scope and the rule or assessment scope to be meaningful.
@343
The project is a defensive review tool. Source should only be uploaded when its owner or an authorised team has granted permission. Demonstration inputs and illustrations should not expose private account details, repository credentials or copies of code that are unnecessary to support the observation. The ability to preserve an audit record does not remove the obligation to minimise the information it contains.
@344
Model-assisted review adds a separate data-handling question. Only the context needed for the task should be supplied, and a suggested change should be reviewed before it is used. Test evidence should come from isolated workspaces or approved fixtures where possible. Tests involving destructive actions or access denial must use data created for that purpose, rather than an existing project audit or an account outside the evaluation scope.
@345
These limits also apply to the thesis. A figure or result should identify what was observed and avoid implying proof of a condition that was not tested. An uncertain finding can still be a useful example of how the interface supports review. Its value lies in showing the developer where to check, not in inflating the number of confirmed vulnerabilities. Where the institution requires a statement on writing or tool assistance, that statement should follow the applicable submission guidelines.
