@391
ThreatLens separates the work of accepting a request from the work of analysing the request and presenting the result. The browser handles interaction through the API. The processing layer prepares eligible files and produces findings. The database retains the audit state, and private storage provides source previews when an authorised reviewer opens them. Figure 1.1 shows these boundaries. The individual pages are different ways to inspect the same saved audit, rather than independent scans of the same upload.
@392
Source preparation and analysis can advance separately. The source view answers whether evidence can be opened, while analysis answers which checks have produced findings. If a preview becomes unavailable, that does not erase a saved finding or make the scan result clean. Conversely, the availability of a file preview does not show that the file has been analysed. The API therefore needs enough information to report the state of each stage without combining the two into one progress indicator.
@393
The scan reference links progress, findings, evidence and the eventual report. It also provides a way to resume review after leaving the page. The browser can keep a reference to the selected audit, but its access to the underlying records is checked again when they are requested. That is important because membership or retention can change after an audit has been run.
@395
The Dashboard summarises recent activity and completed audits. Codebase Audit provides the upload and history entry points. The Workbench places source and finding details beside each other, while Findings supports triage across the selected audit. Attack Graph presents source relationships, Reports provides saved report access, and Security Advisor supports follow-up questions. Each view is designed around a different review task, but links between them should retain the selected audit or finding when one is available.
@396
A reviewer can enter the workflow at several points. Opening an audit from History should show the saved record rather than beginning a new upload. An audit that is still running can be reopened for progress, and a completed audit can be resumed directly at its Workbench. Navigation behaviour should remain separate from account and appearance settings so that changing the interface does not change the record under review.
@397
The interface needs to make the source of the content visible. A Dashboard summary may represent the latest completed audit rather than the one still running. An example graph is not necessarily built from the user's scan. In a narrow layout, the source panel and finding details may be viewed one at a time, but the association between them must survive the switch. The read-only nature of the source view does not change with the size of the screen.
@399
Authentication identifies the user making a request. Authorisation determines whether that identity can perform an action in the chosen workspace. Ownership and membership are therefore evaluated with the requested scan or finding, rather than inferred from the route that opened it. A valid session for one workspace does not grant access to records from another.
@400
Database policies protect workspace records at the data layer. The API also verifies the relationships it acts on, including where an operation is performed using server-side privileges. For example, an authorised scan identifier should not be paired with a finding from a different scan. The source and report endpoints need a corresponding access check because an identifier copied from an earlier session is not current authorisation.
@401
Roles distinguish reading from changes to records or settings. A viewer can be permitted to read shared findings without having the right to delete audits or publish a repository change. Repository actions add a separate GitHub permission check; workspace permission by itself does not supply access to the external repository. The implementation should be evaluated with representative allowed and denied requests, including a membership change while access to an audit is being reviewed.
@403
The local saved-ZIP flow begins with a POST to the workspace's audits endpoint under the versioned API. On acceptance, the API returns HTTP 202 and a scan reference. Acceptance is not a synchronous scan result. The request can carry an idempotency key so that a repeated submission after an uncertain response need not create a second audit.
@404
The processing flow records progress for analysis and source handling. The frontend can retrieve a partial source manifest when it is ready, and the list may grow while file preparation continues. It should not render a pending list as a final count. A completed assessment is presented only after its results have been saved. If source handling fails but findings have been saved, the resulting view should explain which evidence remains accessible.
@405
The audit is associated with the workspace rather than the component that initiated the upload. After a request has been accepted, opening another page does not intentionally cancel it. Returning to Codebase Audit can restore the scoped reference and retrieve the current status. An inaccessible or deleted scan does not become accessible because that reference is still present in the browser; the system revalidates it before showing the audit.
@407
The repository also defines a worker-oriented profile for scans handled outside the API process. In this profile the API and the worker communicate through a task queue, using Celery and Redis. The worker carries out configured processing and updates the saved state. Moving work out of the request process can reduce contention there, but the browser still needs an authoritative status from the application.
@408
This profile has additional operational dependencies. The broker can accept a task before a worker is ready to run it, and an interrupted worker may leave behind an accepted but incomplete operation. Recovery needs to know the saved state before retrying a task. A useful verification would cover queue delay, worker interruption and restart, and confirm that repeated delivery does not create duplicate saved results. These are different checks from verifying the same browser interaction in the local profile.
@409
The available audit captures do not identify a worker deployment for the runs shown in this thesis. The mode is described here as a supported deployment design, without attributing the observed local workflow or its timing to the worker. The comparison in Section 4.6 should be read in that context.
@411
The project uses a common finding structure for rule-based output and other eligible sources of analysis. The normalisation stage makes the path, severity, evidence and origin available to the same review interface. Where an analysis source provides no valid location or score, the common record can retain the rest of the finding without manufacturing the missing field. The original detector or analysis origin remains useful when a reviewer wants to understand why a candidate was reported.
@412
Finding identity matters after normalisation. The same title can appear in several files, while multiple rules can report overlapping evidence within one file. The interface uses saved identities to keep those cases distinct. Filtering selects a subset of saved results and pagination displays part of that subset. Neither changes the audit's overall findings count. A report or export must use the intended collection rather than treating the currently visible page as the complete dataset.
@413
The installed and enabled checks depend on the profile. A saved findings record shows that a result was returned; it does not establish that every listed engine ran. Stage status and coverage information need to accompany the record. If a detector was unavailable, or a file type fell outside the supported set, the report should retain that limit alongside any findings from stages that did finish.
@415
Model-assisted review is intended to explain evidence or provide a starting point for a change. A finding-specific request uses the selected saved finding and a bounded source context, subject to access and availability. It should not take instructions from uploaded code. The output presented to the reviewer is advice, separate from the stored source and separate from any formal proposal that can reach a repository.
@416
The link from the Workbench to Security Advisor should preserve the workspace, scan and finding. Without that association, an apparently relevant answer may be based on a general question instead of the recorded evidence. If the requested finding no longer exists or its evidence has expired, the application should make the limitation clear. A rejected or disconnected request should not be treated as a successful response merely because some text arrived before it stopped.
@417
The remediation view separates an assessment, optional code and suggested verification. This structure gives the reviewer a way to see whether the recommendation is justified before reading the replacement example. An unclosed code block or interrupted answer remains incomplete. A user may review a proposal or request another suggestion, but the system should not execute free-form model output or automatically change a finding's state.
@419
Classification and severity are stored as separate kinds of information. A weakness identifier describes a category, while CVSS 3.1 assigns severity using a defined vector [6]. The vector describes the assumptions under which the score applies. The user interface should preserve a valid zero score and distinguish it from an unavailable score. Converting both cases to a blank value would hide a relevant distinction in the saved record.
@420
A numerical score should not imply more certainty than the evidence provides. If the analysis cannot establish the conditions required for a vector, the reviewer needs to know which assumptions remain unverified. A high score can help decide what to examine first, but it does not confirm reachability or impact in the deployment. An explanation that mentions a possible consequence should be read alongside the actual source location and coverage.
@421
Triage records a separate human decision. A reviewer may leave a candidate open, accept a risk, reject a false positive or close an issue after checking the change. Opening a pull request, passing CI or obtaining a different score in a later scan can inform that decision. None is equivalent to a reviewed change in the finding's state.
@423
Retrieval-augmented generation is an optional way to add reference material to an explanation. The repository includes supporting components for embeddings, vector search and corpus preparation. A retrieval-enabled flow can look up relevant material for a finding before the model writes the explanation. The presence of these modules is evidence of the design; it does not show that retrieval ran for any screenshot presented here.
@424
A useful mapping needs to identify the applicable framework or control and say why the available evidence is relevant. A reference selected because it uses similar vocabulary may still be inappropriate for the case. Reviewers should check the underlying text and the scope of the recommendation. To reproduce this stage, a run should record the corpus version, retrieved reference identifiers and services that were available.
@425
The framework signals displayed by ThreatLens relate to the assessed scope. They cannot cover requirements that depend on organisational procedures, contractual obligations or operational settings missing from the submitted source. A missing reference must remain visible as a coverage limit. The output is a starting point for reviewing controls, rather than a claim that a project complies with an entire legal or technical framework.

The extension-review profile illustrates why policy status is separate from application security severity. A package can provide enough information for an automated manifest check while providing too little to judge how the developer obtains consent. The latter belongs in review or unassessed coverage, not as a pass. The selected store and policy version matter, because two stores can define different obligations for similar behaviour. The policy result should still be linked to its evidence, whether that evidence is a packaged file, a declaration or an identified gap.
@427
The Workbench places files, source, findings and remediation close enough to be used in one review. The source viewer is read-only and can show the line associated with a saved finding when the record supports that location. The evidence panel retains the finding description and available context. Figure 5.1 shows these pieces together. It documents the review interface, not proof that the reported behaviour happened at runtime.
@428
The Attack Graph provides a different view of the same type of evidence. Its nodes organise components and findings around saved source associations. Selecting a relevant node can help the reviewer locate the evidence in a larger set of results. A connector derived from a saved finding does not show a verified network route or demonstrate exploitation. This limit matters because a diagram can look more conclusive than the underlying evidence.
@429
Figure 5.2 uses isolated fixture data to show the graph controls and a selected finding. This makes it possible to explain what selection and evidence inspection do without relying on a live project. Illustrative scenarios should be labelled separately from graphs derived from the user's own audit, even when both use the same layout.
@435
The two figures demonstrate different ways of navigating a finding. The Workbench starts with the code and its saved location. The graph starts with a relationship and guides the reviewer toward the associated evidence. In both cases, the underlying record determines what can be claimed. For a team member who receives a report instead of using either view, the report needs to retain the same distinction between association and confirmation.
@437
The Reports area opens completed saved assessments and prepares a PDF on demand. Preparing a PDF does not rerun the scan or ask the model to generate new evidence. The report uses stored findings, recorded scope and available remediation. This makes it possible to share the audit without suggesting that a newer analysis was performed at the time of download.
@438
Scan history and audit events answer different questions. History helps a reviewer locate a saved assessment and its outcome. Audit events record actions or changes for accountability, where the application records them. A history entry can identify when a scan was started or completed, but does not replace the event record for later actions on its findings or workspace.
@439
Structured exports can also be used to review a selected set of findings. An export should preserve the selection or filter requested and retrieve all matching rows, rather than exporting only the first page visible in the browser. Verification should check the saved identities and the count included in each export. The report itself should remain readable where a value or preview is unavailable, and should communicate the limits of the assessment wherever the findings are read.
@441
Workspace membership connects users to the workspaces in which they can act. A workspace owns scans, and each scan can have a set of findings, scope details and source snapshot metadata. A file preview is stored separately from the structured finding record. The metadata lets a Workbench request the relevant object without putting unrestricted source content into a data row intended for summary views.
@442
Optional features extend those relationships. A repository reference can associate an audit with a repository and commit. A reviewed proposal can refer to an eligible scan and finding. A saved Advisor conversation may be private to the user in the workspace even where the underlying audit is shared. These extensions do not change the meaning of a core scan or automatically grant access to private conversations or repository operations.
@443
Foreign-key relationships prevent some inconsistent records, but they do not determine who may read a valid row or object. Access policies and server checks remain necessary. Record deletion and expiry also have different effects. Removing an audit can make its findings and related metadata unavailable, while retained private objects may require a separate cleanup step. Expiry of source previews by itself should not erase the assessment's non-source history.
@445
The versioned API separates commands from read operations. The upload command acknowledges an accepted job, while progress and overview requests read its changing state. Bounded list requests load source entries or findings in parts. The source file endpoint returns a bounded line window, allowing the viewer to retrieve an excerpt without requiring all source files to be sent to the browser together.
@446
These contracts allow each interface to report failure at the correct point. For example, an account may have a valid session but lack permission for the chosen workspace, or an audit may be accessible while its preview has expired. These responses should not be shown as the same error. When a network response is delayed, the client must also distinguish a request that was never accepted from an accepted audit that is still processing.
@447
Reloading a safe read after a recoverable failure is different from replaying a command. Uploads and publishing can change persistent state. Retrying these operations requires ownership of the original request or an explicit decision, supported by an idempotency key or saved operation state where provided. Diagnostic records should identify the operation and error category without copying account credentials or uploaded source into logs.
@449
An upload passes through several defensive boundaries. Archive validation limits paths and expansion before file inspection. Source previews are bounded and sensitive values may be masked. Access to the preview is checked in the scope of the audit. These controls address different risks; passing an archive validation step does not grant access to the extracted files, and redaction does not make the files suitable for public distribution.

The package type also influences file selection. A general source audit may exclude build output to avoid reviewing generated files twice. Packaged browser extensions are a different case: a bundled script may be exactly what the store and user receive. The extension profile therefore treats shipped files as assessment inputs where supported. It inspects the package without installing the extension or fetching the referenced remote resources. Runtime behaviour and user consent remain matters for separate verification when they cannot be established from the package.
@450
The system does not need to run the uploaded program to perform static inspection. Supported dependency checks should not install packages from the submitted input on the API host. Report rendering uses saved content and restricts access to external resources. Generated remediation stays read-only in the Workbench. Any supported repository publication is a separate, approved operation using a new branch and pull request rather than a silent edit to the target branch.
@451
The controls should be tested through the failures they are designed to handle. Archive checks need malformed or oversized inputs, access checks need denied and revoked users, and report handling needs saved text that is rendered safely. A successful run in one profile cannot establish that all of these controls work in another. Status and error messages also matter: the user needs to know when the system stopped rather than being left with a result that appears complete.
@453
The frontend production build is served by a standalone Node.js process. FastAPI runs separately, and the configured deployment profile determines whether background work also runs in a separate service. This separation lets the browser application and API be built and checked independently. It also means that a healthy frontend response alone does not establish that backend services are reachable or correctly configured.
@454
Client and API configuration must agree on the intended identity project, and permitted origins must match the deployed browser application. Optional model and repository integrations have their own configuration and access rules. Being able to sign in with an identity provider is not sufficient to perform a repository operation. A deployment check should exercise the operations the environment is expected to support, and mark optional services as unavailable where they have not been set up.
@455
A repeatable configuration records the selected profile, revision, dependency set and enabled capabilities. Frontend settings that are intended for the browser belong on the client side; server credentials remain outside browser bundles and thesis evidence. The configuration described here documents how the services fit together. It does not claim that all profiles or integrations were verified on a hosted instance for the captures in Chapter 6.

A practical deployment check starts by confirming that a permitted account can open its workspace and an unpermitted account cannot. It can then follow a small authorised fixture through acceptance, source review and report download. The fixture should be retained only for the time needed to check the outcome. If repository or extension features are part of the profile, they need separate fixtures and an explicit record of which permissions and external services were used. These checks help establish what the running release supports without using a production repository as the test environment.

The same checks provide a useful distinction when a service is unavailable. A frontend that can serve the sign-in page is not necessarily ready to accept a scan. A deployment that can save static findings may still lack an optional model provider. The appropriate conclusion should name the working path and the capability that was not verified. This is the basis on which the observed outcomes are presented in the next chapter.
