@459
This chapter reviews application captures dated 12 November 2026 and separately documented test results. The captures show how ThreatLens presents saved evidence during a review. The test records describe checks run for particular implementations, with their own scope and limitations. The two sources are useful for different questions. They should not be combined into one result set or interpreted as measurements from a single experiment.
@460
The principal demonstration followed a saved application audit through the Workbench, findings and the report. The observed evidence was a source selection linked to a candidate finding, a visible findings count, coverage information and a report excerpt. This is enough to discuss the review workflow. It does not establish that each available analysis engine ran or that an independently labelled dataset was scanned.
@461
The exact application revision, machine specification, enabled engines and model or corpus settings were not recorded with every capture. Section 4.1 describes the known development environment and distinguishes it from a fully specified benchmark environment. Because those details are incomplete, the demonstration is not used to estimate performance or compare analysis profiles.
@462
The study reports an outcome only at the level supported by its record. An interface capture can establish an observed state but rarely the full set of actions leading to it. A regression log can identify a checked behaviour if the test and expected result are known. An experimental conclusion about detection would require a different record, including independent labels and a consistent matching process.
@464
Ground truth should identify the weakness, its location and the relevant code behaviour independently of the detector. A corrected counterpart helps show that the detector is reacting to the weakness and not simply to a familiar API or file pattern. Similar benign cases are useful for much the same reason. For these cases, reviewers should record why the condition is absent, not only that the scanner returned no finding.
@465
The saved project alerts could not serve as their own ground truth. Counting every candidate as valid would measure agreement with the system's own output rather than its ability to detect independently established issues. A sound comparison also needs a process for adjudicating disputed cases. If a reviewer cannot determine whether a condition is present, the case should remain unresolved in the recorded results.
@466
The available engine-results worksheet was a template without completed observations. There was no matched inventory with independently labelled positives, verified clean controls and a corresponding set of engine outputs for the application captures. This limits the chapter to functional evidence and discussion of individual saved candidates. It also prevents constructing an evidence-based bar chart or ranking of the scanners.
@467
For a future evaluation, each project should have a stable identifier, an input checksum and a reviewable set of expected issues. If a private project must be described without its name, those identifiers can be recorded in an appropriately restricted run log. Anonymising a project does not remove the need to account for how it was selected, what it contained, or which files the tools were able to analyse.
@469
Table 6.1 separates the expected outcome of each functional case from the evidence retained for this chapter. Reopening an audit, for example, should demonstrate that the same server-side reference survives navigation. Seeing a completed item in History is not enough to prove that a recent upload resumed without duplication. The observation has to cover the state change being tested.
@470
The retained Workbench observation shows a selected finding alongside the source view. The report observation shows saved evidence and remediation in an exported document. These are useful demonstrations of working output paths. Neither observation includes a complete test trace for all possible selections, every PDF entry, or every possible access role. The table makes that difference explicit.
@471
The verification plan also includes denied requests, unavailable source, errors from optional services and malformed uploads. Section 6.8 records a separate set of historical regression checks where the project notes describe the scenarios. Cases not observed in the main capture are not treated as failures; they are left unverified for that evidence set.
@474
The saved MERN application audit contains six reported findings. The figures show the information presented to the reviewer, including severity, source references and guidance where available. These six records describe the output of the audit. The study does not treat them as six independently confirmed vulnerabilities or as the sum of all weaknesses present in the application.
@475
The saved evidence also illustrates why a title should be read together with the source. A location may contain a short expression but miss the caller, entry point or data origin needed to establish the reported condition. A productive review starts with the recorded file and then checks the surrounding code and assumptions. Where that context is missing, the result remains a candidate for review.
@476
The Workbench capture lists 90 preview entries, while the related reporting evidence records 81 scanned files. The two counts refer to different stages. Without a matched file inventory, their difference cannot be interpreted as nine particular excluded files, nor can the counts be used to calculate detector recall. What they establish is that source availability and analysed-file coverage are not interchangeable.
@477
Figure 6.1 shows how the saved report presents the evidence, remediation and suggested verification. The report extends review beyond the browser session and retains useful context. The figure does not establish complete data parity across every page, nor does it show that any suggested check was executed. A separate parity test would compare every report entry with the saved assessment under the same scope.

For someone reading the result outside the application, the excerpt also shows why the report needs to name the source of each statement. The path and recorded code describe evidence retained by the audit. The remediation describes a possible change, and the verification section describes checks that a reviewer could perform. If these are presented as one undifferentiated narrative, the reader may conclude that the suggested change was already applied or that the check passed. The excerpt supports a check of the presentation of those categories, not of the outcome of the suggested test.
@481
No precision, recall or F1 result is reported for the demonstration audit. The necessary true-positive, false-positive and false-negative counts were not available. A high number of reported items can reflect either useful coverage or additional review work; a low number can reflect either a cleaner sample or limited coverage. Without the reference set, neither pattern can be interpreted reliably.
@482
When evaluating several engines, the unit of comparison matters. If two engines report the same weakness at the same underlying location, the combined result should receive one match, with both origins retained. Two weak points in different files should not be collapsed only because their titles match. These rules need to be fixed before the counts are compared. Changing the matching policy after seeing the results can change the apparent ranking.
@483
Aggregate metrics should be accompanied by the number of supported examples in each relevant category. A tool may perform well on a language represented by many fixtures while providing little evidence on another. Precision by group and recall by group can make that imbalance visible. An unsupported language or a skipped analysis stage should be shown as a coverage limitation instead of disappearing from the dataset summary.
@484
A useful results table would report the matched counts, unresolved candidates and scope alongside the derived measures. A future figure comparing engines should use those same numbers and identify its denominator. The saved demonstration outputs do not support such a figure, so the chapter retains the case-based evidence rather than substituting estimated or illustrative performance values.
@486
Performance has several user-visible boundaries. A scan can be accepted before any source is available; a preview can appear before analysis has finished; and the Workbench may still wait for a saved final result after processing. Useful timing therefore identifies the beginning and end of each measurement. Total elapsed time should be measured directly from defined events, not inferred by adding the stage durations.
@487
A repeatable test would use the same input, enabled stages and service profile for several runs, and would report the number of runs as well as a median and range. Runs with a warm cache can be reported separately from first runs. If queueing or a remote service is part of the path, that time should be identified. A timeout or skipped stage also belongs in the record, since it changes the interpretation of any reported duration.
@488
Some stages can overlap. Source preparation may take place while analysis is already running, so adding them would count part of the waiting time twice. The useful engineering diagnosis is to determine which phase delayed the visible result. Separate timestamps for acceptance, first preview, analysis and result persistence provide more information than one number for the whole request.
@489
The selected application captures did not include a timing series with these boundaries. No median scan duration or performance improvement is therefore asserted for them. The project does contain isolated feature demonstrations from other profiles; those can document a working flow, but their elapsed times cannot be used as a comparable benchmark for the saved MERN audit.
@491
The model-assisted review should be assessed on whether it stays close to the saved evidence. A good explanation identifies the observed operation, states the additional condition that would make it unsafe, and makes any uncertainty clear. A proposed change should then explain the behaviour it aims to preserve and name a useful check. Polished wording alone does not establish any of these properties.
@492
The portal audit provides an example involving fixed SVG markup assigned through an HTML insertion operation. The excerpt establishes that the operation was used. It does not show attacker-controlled input reaching it. The useful distinction is between a risky operation in the general case and the specific evidence available here. If an alternative implementation is suggested, the reviewer should check that it preserves the SVG structure and the password visibility behaviour. The saved answer is not evidence that a proposed replacement was executed or verified.
@493
Retrieval and remediation require different evaluations. Retrieval should be checked against a set of reference passages or controls independently judged relevant. Remediation should be checked against the application behaviour and the original issue. A retrieved document can be relevant even if a proposed code change is incorrect. Conversely, a reasonable change may be proposed without proving that retrieval helped. The two outcomes should be recorded separately.
@494
The available material gives examples of contextual guidance, but it does not include enough independent reviewer ratings, adjudicated retrieval cases or tested patches to quantify improvement. Cases where the evidence does not justify changing code should be included in a larger study. Otherwise, a model could be rewarded for always proposing a change, even when restraint would produce a better review outcome.
@496
Robustness concerns what happens when a normal request cannot finish. Relevant cases include malformed input, a revoked member, expired source and an interrupted response from a provider. Expected behaviour depends on the failure. Missing access should prevent disclosure. Expired source should prevent preview without rewriting the history of the audit. A provider interruption should remain distinguishable from a completed answer.
@497
The project's extension-review implementation record documents a separate set of regression checks: 360 backend tests passed, five environment-dependent tests were skipped, and 72 frontend checks passed. The same record notes 437 checks in isolated PostgreSQL for access and related data behaviour, including viewer, outsider and revoked-member cases. These are historical results for the documented feature and test configurations, not checks independently rerun for this thesis revision.
@498
The same notes describe a disposable hosted extension-review workflow using synthetic packages and test accounts. It exercised report download and selected access restrictions. The primary model provider failed authorisation in that run and a fallback completed the model-assisted step. This supports the narrower observation that the configured fallback worked in that test. It does not establish that the primary provider was functional or that every upload profile handles an outage in the same way.
@499
The limits of these records are important. A test in isolated PostgreSQL does not by itself verify every hosted configuration. A hosted extension-review workflow does not exercise every original ZIP or worker path. The author's application captures and the historical regressions can support one another where they concern the same behaviour, but neither should be used to claim broader verification than the relevant record describes.

One way to make the separation more useful in a future release is to retain a small evidence pack for each acceptance test. A test for expired source would record the availability of the finding before and after expiry, as well as the response when the preview is requested. A test for a provider interruption would record whether partial advice was visibly marked and whether the saved result remained intact. These records would give precise answers about individual failure paths without requiring broad claims about all deployments.
@501
A controlled baseline would compare static-only operation with the combined workflow on the same labelled inputs. It would use the same rules for eligible files and matching results, and would retain cases where a stage is unsupported. That makes the comparison about the contribution of the additional analysis rather than about two groups of projects with different content.
@502
If retrieval is being compared, the model and generation settings should be held constant where possible. Prompts should ask for the same task and the evaluation should use the same independent relevance judgements. For runtime measurements, the reference corpus, model-service conditions and queue settings should be recorded. Without these controls, the difference could come from configuration or availability rather than the feature under evaluation.
@503
No completed controlled baseline was available for this chapter. The literature comparison describes features and purposes, not measured performance under a common protocol. The saved application audit cannot show that a combined run performs better than its static baseline, or that one named engine is faster or more accurate than another.
@504
The remaining comparison should be built from test inputs and outcomes that another reviewer can trace. It would report the number of labelled cases, deduplicated results, unresolved findings and any skipped stage. If the combined workflow improves explanation but does not change detection, that is a useful finding in its own right. It should not be turned into a detection improvement simply because it contributes to the same user workflow.
@506
For the first research question, the observed interfaces show that scan outputs can be reviewed through a shared record containing the source location and recorded evidence. The model-assisted example illustrates how that evidence can inform an explanation. This is a demonstration of the integration, not a systematic check of provenance across all engines. For the second question, the Workbench and report show how a reviewer can read recorded evidence separately from suggested changes. The SVG case shows why that distinction matters: a useful explanation can still describe the evidence as insufficient to confirm a vulnerability.
@507
The third question asks how findings and policy assessments can be presented together without confusing severity, policy outcome and coverage. The extension-review design and test record provide an example: a security finding and an unassessed policy requirement can be reported separately. That separation does not establish that every policy decision is correct. The fourth question concerns how well the workflow handles access restrictions, incomplete processing, unavailable services and reopening. The historical tests support specific cases, such as revoked access and provider fallback, while the saved captures show reopening and review states. They do not establish reliability across every failure mode or deployment.
@508
ThreatLens is therefore strongest as a tool for organising a review, showing where the evidence comes from and making unresolved questions visible. The limitations are concrete: available file coverage varies, external services may not run, and source excerpts can leave important conditions unverified. A broader validation should test the system where those limitations are most likely to affect a review decision rather than treating successful demonstration cases as typical of all audits.
