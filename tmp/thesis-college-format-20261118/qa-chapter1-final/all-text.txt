ABSTRACT
Security assessment is often treated as a separate activity from software development.
Developers may receive vulnerability reports that identify a problem but provide little
context about the affected code, its potential impact, or the steps needed to address it.
Compliance requirements add another challenge, particularly when technical findings
must be connected to documented controls or browser-extension store policies. These
gaps make security review difficult to interpret and act upon, especially for small
development teams.
This thesis presents ThreatLens, a web-based platform that brings codebase auditing,
threat modeling, compliance assessment, and remediation guidance into a single
workflow. Users can submit project archives for analysis and examine saved results
through a read-only, editor-style workbench. The platform combines static security
checks with language-model-assisted analysis to identify potential weaknesses and
provide explanations grounded in available source evidence. Findings include severity,
recorded file locations, relevant code excerpts, and remediation guidance.
The workbench connects source files with findings, control mappings, and suggested
verification steps. An evidence-based graph helps users explore relationships between
findings and affected components without presenting those relationships as confirmed
exploitation paths. Security Advisor provides contextual explanations and code
suggestions, while keeping proposed changes separate from the uploaded source.
Browser-extension reviews extend this workflow to Chrome Web Store and Microsoft
Edge Add-ons policies, distinguishing detected violations from requirements that need
manual review or cannot be assessed from the submitted package.
ThreatLens also provides saved audit history, finding triage, comparison of compatible
extension reviews, and downloadable reports. Workspace authorization, private source
storage, evidence redaction, and time-limited source previews support controlled access
to sensitive project information. Verification covers automated regressions, access-
control checks, report generation, and representative browser workflows; these checks

accuracy.
The principal contribution is an integrated, traceable review workflow that helps
developers move from a reported concern to its supporting evidence, possible remedy,
and verification approach. ThreatLens supports informed security decisions, but does not
replace manual testing, professional assessment, or official compliance and store-
approval processes.

1.1 Background and Motivation
Software applications handle personal information and business transactions. They also
carry messages and give people access to essential services. A decision made while
writing a single part of an application, such as where to check a permission or how to
store a sensitive value, can affect all the users who depend on it. Input validation and
database query construction are similarly easy to overlook when the immediate goal is
to make a feature work. Security review belongs in the development process while there
is still time to inspect and change those decisions. The National Institute of Standards and
Technology (NIST) makes this point in its Secure Software Development Framework,
which places security practices throughout the software development life cycle. [1]
As a project grows, the work of checking a warning is seldom confined to the line named
in the alert. The developer may need to follow a value from the file in which it arrives to
the file in which it is used. A framework may handle one step, while a library or a local
helper handles another. The review then becomes a question of which checks are already
in place and what would happen if the proposed correction changed the way the
application behaves.
Consider an ordinary review after a change to an account page. A developer receives a
warning and opens the affected file. To decide whether to act, they need the original
location, enough surrounding code to understand it and a clear account of what the
warning means. If the finding is still open when another developer returns to the audit,
those details should be available without reconstructing the investigation from memory.
This is the part of source review that motivates ThreatLens.
Static Application Security Testing (SAST) examines source without running the
application. It can point a reviewer towards code worth checking, including unsafe output
handling, injection-prone operations and possible exposure of credentials. The reported
line is where the investigation starts. A rule can raise an alert for code that is safe in
context, and it can miss behaviour that depends on application state or business rules.
The reviewer still has to look at the code before classifying the issue. [2]
6

PAGE 18
A language model can explain an unfamiliar operation or draft a possible remedy. That
help is useful when a scanner has identified a concrete issue but its message leaves the
developer unsure what to change. The explanation may also make assumptions about
code the model has not seen. NIST describes plausible, unsupported model output as
confabulation and recommends evaluating generated output and checking the sources
that support it. In an audit, that means keeping each generated explanation beside the
evidence it discusses so a reviewer can check the two against one another. [3]
We developed ThreatLens to support review from the time a project is submitted to the
time a finding is revisited or reported. A developer can follow the progress of an analysis,
open a saved finding and inspect the available source before deciding on the next step.
The purpose of the workflow is to make that decision easier to trace. The decision itself
still belongs to the reviewer.
1.2 Problem Statement
An automated warning has practical value when a developer can connect it to a specific
part of the application. A category name alone cannot tell the reviewer which statement
caused the warning or whether it matters in the conditions where the software runs.
Before proposing a fix, the reviewer needs to establish whether input can reach the
recorded operation and whether a check elsewhere already prevents the unsafe case. A
useful finding supplies the location and evidence for that investigation.
An HTML update provides a simple example. Assigning a fixed, trusted value and
assigning a value that an outside user can influence require different conclusions, even
when both uses appear on the same kind of line. The recorded evidence can establish
that the update occurs. It may leave the origin of the value or the surrounding protections
unclear. In that situation, asking the developer to check the value and its path is more
useful than presenting the warning as confirmed cross-site scripting or promising that a
replacement will fix it.
The same distinction affects remediation. A change may address the operation a scanner
recognised while failing to address the actual source of the problem. It may also alter a
7

PAGE 19
legitimate part of the interface. A proposed remedy is easier to assess when it says what
behaviour must stay the same and which checks would show that the change is
acceptable.
Reviewers also need a way to decide what to look at first. The Common Vulnerability
Scoring System (CVSS) describes technical severity. FIRST treats that score as one input
to vulnerability management, where the organisation and its environment still matter. A
high score can justify earlier review, but a developer still needs to know whether the
affected function is available in their deployment and what the application depends on it
for. ThreatLens therefore presents severity as a property of the finding and leaves the
decision about operational priority to the reviewer. [4]
A review system has to show what happened when an audit could not run to completion.
Uploaded archives are untrusted, and recovery from a failure must not make a partially
analysed project appear clean. The source preview may be preparing while analysis runs.
An external service may be unavailable. A developer may leave the page and return to
the audit later. Each condition calls for a different explanation because it leaves a
different amount of evidence available to the reviewer.
For instance, an accepted upload means the service received and recorded the
submission. It does not mean that every check ran or that the result is ready. If a preview
later expires, the report may still be available. The interface should make clear that the
evidence is limited by the expired preview rather than suggesting that the finding has
disappeared.
The problem addressed here is how to connect automated checks to a review process
that people can understand and repeat. ThreatLens needs to keep each finding tied to
the evidence that produced it, offer remediation that can be checked and restrict private
material to the people authorised to see it. The resulting audit should tell the reader what
the system assessed and where its assessment stopped.

1.3 Existing Approaches and Challenges
In a manual review, the reviewer can ask whether a piece of code behaves as the
application intended and whether it follows the business rules that apply to it. That
context is especially useful when a general scanner rule would make little sense on its
own. Manual review depends on the time and experience available, though. Two
reviewers may also follow different paths through a large project unless the scope and
the evidence they inspected are recorded.
Rule-based scanners help with checks that can be repeated over the same files. Different
scanners can describe the same underlying condition using different names or point to
different parts of it. Conversely, the same rule can identify separate occurrences that
need separate review. Consolidation has to keep enough information to tell these cases
apart. If a result is combined with another one, the reviewer should still be able to see
where the original evidence came from.
A conversational assistant can explain a finding in terms familiar to the developer. An
answer given without the exact source version may fit a similar-looking example and still
be wrong for the saved audit. In ThreatLens, finding-specific guidance uses the evidence
available to the authorised reviewer. The suggestion appears separately from the
uploaded source so an example can be read without assuming that it is part of the original
code.
Some compliance questions cannot be answered from source alone. Chrome Web Store
policies cover the extension and the way it is presented, including declarations and
marketing materials. Microsoft Edge Add-ons policies also consider matters such as
permissions, privacy, functionality and changes to browser settings. A built extension ZIP
can show what is in the package or which permissions the extension requests. It may not
tell the reviewer what the developer disclosed or whether the user saw an appropriate
explanation. Those questions may require a declaration or a manual check. [5] [6]
The same record can therefore contain several kinds of information. A scanner alert
records an observation. A suggested control mapping gives the reviewer a policy to
9

PAGE 21
consider. A model response may explain either item, and a reviewer can record a decision
separately. Keeping these entries distinct lets a reader see what was measured, what was
suggested and what still needs evidence.
1.4 Research Gap
The research gap addressed by this thesis is how automated results can be carried into
an assessment that remains traceable as the reviewer moves between views and returns
to a saved audit. Tools already exist for parts of that work. This study examines their
integration within ThreatLens and asks what evidence would show that the integrated
workflow behaves as intended.
The first issue is continuity of evidence. A developer should be able to open a finding in
the Audit Workbench, select it again in Findings, and recognise the same record in the
Attack Graph, Security Advisor and Reports. The title of a finding may be shared by more
than one occurrence, so a title is a poor substitute for its audit, file location and recorded
evidence. Each view can serve a different purpose while still making it clear which finding
is under review.
That requirement becomes more important when a view is filtered or only some records
have loaded. A count can be accurate for the view shown and still differ from the saved
audit total. The interface needs to say which count it presents. An evidence link should
likewise keep its original audit and location, even when the source excerpt is temporarily
unavailable.
The second issue is how to interpret remediation guidance. A reviewer should be able to
see which part of a suggestion comes from the evidence and which part depends on an
assumption about the application. The proposed change must remain separate from the
original code. Its status should also be clear: generating a suggestion shows that the
system produced a response, while applying a change and checking it are separate
actions.
The third issue is how to assess coverage and correctness. A completed job means the
scan reached its end state. It may still leave files, vulnerability classes or policy
10

PAGE 22
requirements outside the assessment. Evaluation therefore needs to identify the input
that was eligible, the evidence saved, and the checks the system did not perform. Access
isolation and consistent reporting can be tested with known cases. Detection accuracy
requires a different comparison against independent labels.
These issues define what the integration has to demonstrate. The implementation can
be examined through known workflows and their saved evidence. A claim that the
combined system detects more vulnerabilities than another method would require a
controlled comparison beyond that implementation check.
1.5 Aim and Objectives
The aim of the project is to develop and evaluate ThreatLens as an AI-assisted framework
for automated source-code security assessment, vulnerability prioritisation and
compliance analysis. The work starts from recorded source evidence and gives
developers a way to inspect a finding before deciding whether to act on it.
The project objectives are:
• Provide an authenticated submission route that validates supported project inputs
and prepares the source for assessment.
• Combine static checks with language-model-assisted analysis while keeping the origin
and source evidence of each finding.
• Organise findings in a consistent form with the file location, vulnerability category,
available severity information and review status.
• Provide a read-only Audit Workbench where developers can inspect source, findings,
remediation steps and suggested checks.
• Offer explanations and code suggestions on request, separate from the uploaded code
and subject to review before use.
• Show evidence relationships and relevant compliance mappings while identifying
which paths and controls still need verification.
11

PAGE 23
• Preserve audit history and reports so authorised reviewers can reopen results at a
later stage.
• Use documented test cases and fixtures to examine workflow behaviour, evidence
consistency, access restrictions, failure handling and interface responsiveness.
The objectives define a review workflow; they do not require unrestricted execution of
uploaded projects or automatic acceptance of generated fixes. Detection is bounded by
the checks performed and the evidence those checks can reach.
1.6 Research Questions
The project addresses four research questions.
RQ1. How can static security checks and language-model-assisted analysis be combined
while preserving the source location, provenance and supporting evidence of each
finding?
RQ2. How can an editor-style workbench present findings, severity information and
remediation guidance so that users can distinguish recorded facts from assumptions and
generated suggestions?
RQ3. How can security findings and compliance assessments be presented together
without confusing vulnerability severity, policy outcomes and unassessed requirements?
RQ4. How reliably does the implemented workflow handle authorised access, incomplete
scans, unavailable services, source expiry and the reopening of saved results?
The four questions call for different kinds of evidence. The first two can be investigated
by following known findings from analysis into the Workbench and checking which source
evidence remains available. The third calls for a review of policies with different evidence
requirements, such as a check the package can answer and one that still needs a
developer declaration. The fourth concerns how the system behaves when access
changes, processing is incomplete or source is no longer available.
Repeatable tests can establish whether the workflow handles those cases consistently.
They cannot establish precision or recall unless the expected results were independently

labelled and a procedure was set for matching findings to those labels. In the same way,
a screenshot can show what is available on a page, but a usability study would be needed
to tell whether reviewers can interpret it reliably.
1.7 Project Scope and Limitations
The main workflow covers submitted source projects and saved audit results. A
developer supplies a project ZIP, and the service prepares source previews as they
become available. Recorded findings can then be examined in the read-only Workbench.
Related views support filtering, triage, evidence relationships, contextual guidance and
report downloads. Repository features depend on the required GitHub setup and the
permissions of the person using them.
ThreatLens also reviews built ZIP packages intended for the Chrome Web Store or
Microsoft Edge Add-ons. The review compares available package evidence and supplied
declarations with versioned policy references. It distinguishes violations detected by the
checks from requirements that need human review, remain unassessed or do not apply.
ThreatLens does not install the extension, inspect the developer's browser settings or
submit the package to a store.
The extension package illustrates a wider limit of the project. A package may contain
enough information to compare a declared permission with a policy. A separate
requirement may depend on behaviour or information outside that package. If the
reviewer cannot obtain that evidence, an unassessed status conveys more than a pass
would. The store makes its own approval decision.
Assessment is bounded by the source that is available, the supported analysis methods,
the input limits and the services configured for the run. Static checks do not reproduce
every runtime condition or establish that the application follows every business rule.
Model explanations can also be wrong. A report with no recorded findings shows what
the completed assessment recorded for the supplied input. It cannot rule out weaknesses
outside that coverage.
13

PAGE 25
Remediation suggestions require review and testing. When repository publishing is
configured, an authorised user can review a diff and publish it through a separate branch
and pull request. The workflow does not change the target branch automatically. A
proposed change, a structural validation check and an open pull request each provide a
different record of progress. None establishes on its own that the original finding has
been resolved.
Project information is restricted through authenticated workspace access and private
source storage. Source previews are available for a defined period. Saved findings and
reports have their own history, so a reviewer may be able to revisit the audit after the
preview has expired. Where the deployment uses an external model service, service
availability and the way the configuration handles submitted material also need to be
considered when projects are selected for assessment.
These limits matter when interpreting results. A past report can establish what the
system recorded at the time of the audit. If its underlying preview is no longer available,
the report cannot substitute for the original source when a reviewer needs to test a
detailed explanation. That follow-up may require a new audit of an authorised copy of
the project.

Contribution 1. Integrated audit workflow.
ThreatLens brings project submission, analysis progress, source review, finding

Contribution 3. Controlled remediation presentation.

Contribution 6. Verification of supporting system behaviour.
Documented checks address access isolation, scan state handling, source availability,
report completeness and interface responsiveness. These checks are useful when they
reproduce a situation a reviewer would encounter. For example, a test that reopens a
saved scan checks whether the workflow retains the result. It says nothing about how
many vulnerabilities the detector missed.
The contribution of this work is the way the system connects those review functions and
records the evidence available at each step. ThreatLens uses language models as part of
that workflow and relies on a reviewer to decide which findings and suggestions are

2.1 Introduction to Software Vulnerability Detection
Vulnerability detection attempts to identify conditions that may allow software to
behave insecurely. A useful assessment distinguishes a suspicious construct from a
demonstrated vulnerability. The meaning of an alert depends on data flow, validation,
configuration and runtime conditions.
Different analysis methods provide different forms of evidence. Some recognise known
patterns, while others reason about dependencies, source relationships or likely
behaviour. Human review remains important because an automated tool may not have
enough information to determine whether a reported condition is reachable or
exploitable.
This chapter considers these complementary methods and their relevance to ThreatLens.
It does not assume that combining several tools automatically improves detection
accuracy.
2.2 Static Application Security Testing (SAST)
Static analysis examines code without running the target application. Depending on the
tool, it may use pattern matching, syntax trees, control-flow analysis or data-flow
reasoning.
OWASP describes taint analysis as following untrusted data from a source towards a
potentially dangerous sink [1]. This helps reviewers understand whether external input
can reach a sensitive operation without appropriate handling.
The usefulness of static analysis depends on the supported language, rules and available
context. Framework-specific behaviour, dynamic execution and incomplete source
information can limit the analysis. A reported pattern should therefore lead to
investigation rather than an automatic claim that exploitation is possible.
20

PAGE 32
2.3 Dependency, Secret and Configuration Analysis
Dependency analysis examines the packages used by an application and their recorded
versions. Secret detection looks for credentials or similar sensitive values. Configuration
analysis examines settings that influence deployment and application behaviour.
These tasks require different evidence. A package finding needs reliable version
information, whereas a suspected secret requires contextual interpretation. A token-
shaped string may be a placeholder, a test value or a genuine credential.
SecretBench provides a labelled dataset intended to support research on software-secret
detection [2]. Its methodological relevance is that evaluation requires both genuine
examples and misleading look-alike values. A collection containing only successful
detections cannot adequately measure false alarms.
2.4 AI and Large Language Models for Code Security
Language models can relate a code fragment to a natural-language explanation and
suggest possible changes. Zhou and colleagues review research on their use in
vulnerability detection and repair [3].
This literature provides a foundation for exploring model-assisted review, but it does not
establish the accuracy of the provider, model or prompts selected for ThreatLens.
Generated explanations must be checked against the submitted source.
The need for review becomes particularly important when the model receives only part
of a file or lacks runtime context. A convincing explanation may still overstate the
evidence, misunderstand an application-specific assumption or propose a change that
alters intended behaviour.
2.5 Retrieval-Augmented Generation in Security Analysis
Retrieval-augmented generation combines generated responses with retrieved
reference material. Lewis and colleagues describe an approach that incorporates an
external retrieval mechanism into knowledge-intensive language tasks [4].
21

PAGE 33
In security review, reference material may include weakness descriptions, secure-
development guidance or control clauses. Retrieved passages can help explain why a
finding may relate to a particular requirement.
However, finding a relevant passage and interpreting it correctly are separate tasks.
Retrieval supplies context; it does not independently verify a vulnerability or settle a
compliance question. The reference source and the reasoning behind each proposed
relationship must remain available for inspection.
2.6 Vulnerability Taxonomies and CVSS Prioritization
MITRE’s Common Weakness Enumeration provides a vocabulary for describing
categories of software and hardware weaknesses [5]. It helps organise findings using
consistent terminology.
The Common Vulnerability Scoring System serves a different purpose. CVSS characterises
vulnerability severity through defined metrics [6]. A weakness identifier is not a severity
score, and neither is a triage decision.
Keeping these concepts separate prevents misleading interpretations. A critical severity
label describes potential seriousness under stated assumptions. An open status describes
the current review state. A control mapping describes a possible relationship to a
requirement. These fields should not be treated as interchangeable.
2.7 Compliance Mapping and Remediation Guidance
Compliance mapping links an observation to a potentially relevant requirement. A useful
mapping explains why the requirement applies and identifies any supporting evidence
that is still missing.
Many obligations concern organisational procedures, staff responsibilities or operational
controls that cannot be established from a repository alone. Source inspection can
support part of an assessment, but it cannot demonstrate every aspect of compliance.
Remediation guidance has a similar limitation. A recommendation should identify its
assumptions, expected behavioural effects and suggested verification steps. ThreatLens
22

PAGE 34
treats both mapping and remediation as assistance for a reviewer rather than a substitute
for professional assessment.
2.8 Comparison with Existing Security Assessment Tools
The comparison in this study is organised by method rather than unsupported product
rankings.
Static analysis contributes repeatable rule-based checks. Dependency and secret tools
provide specialised inspection. Model-assisted review contributes explanations and
contextual reasoning. Manual review contributes application knowledge and judgement.
These roles overlap, but they are not interchangeable. ThreatLens is considered as a
workflow that combines and presents evidence. Claims of better precision, recall or
performance require controlled baseline experiments rather than a comparison of
interface features.

2.9 Comparative Literature Synthesis
The selected sources address different levels of the problem. OWASP explains analysis

2.10 Consolidated Research Gap
The resulting research focus is a traceable connection among source material, analysis
outputs, control references and reviewer actions.
The study must also separate technical integration from demonstrated benefit. A
platform may successfully combine tools while still producing unnecessary alerts or
incomplete recommendations.
The research gap is therefore addressed through both implementation and an evaluation
protocol. Coverage, detection quality, usability and operational behaviour must be
assessed independently before broader claims can be made.

3.10 Evaluation Metrics
Detection quality is measured using independently labelled reference cases.
Let:
1. TP represent correctly identified labelled defects.
1. FP represent incorrectly reported defects.
1. FN represent labelled defects that were missed.

The metrics are:
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1-score = 2TP / (2TP + FP + FN)
A zero denominator should be handled using a stated convention rather than silently
treated as a perfect result.
Timing metrics should distinguish acceptance-to-first-preview, analysis, persistence and
end-to-end completion. Coverage should report analysed files against eligible files, with
exclusions explained.

6.8 Robustness, Security and Error Handling
Robustness testing should deliberately interrupt the normal workflow. Relevant cases

responses and unavailable services.

7.3 Limitations and Final Remarks
• ThreatLens should be understood as assistance for developers and reviewers, not an
automatic security authority.

care with which findings are interpreted. A repository cannot demonstrate every

visible. Its strongest supported contribution is the integration of review tasks, not a
guarantee that uploaded software is secure.

FUTURE SCOPE

PAGE 67
8.1 Scanning Coverage and Language Support
• Future work should broaden language and framework coverage through explicit
parser support and documented rules.
• Cross-file reasoning and runtime-aware validation may address cases that isolated
snippets cannot explain. New capabilities should include benign examples, vulnerable
fixtures and clear exclusion rules.
• Packaged extensions and infrastructure configurations require their own assessment
profiles. They should not be described as fully covered merely because their files can
be uploaded.
8.2 AI and Retrieval Improvements
• Model and retrieval improvements should begin with evaluation data rather than an
assumption that a larger model will perform better.
• Useful directions include versioned control corpora, relevance judgements, prompt
comparisons and checks for unsupported explanations.
• Context selection should preserve the evidence needed to investigate a finding while
respecting privacy and input limits. Claims of reduced hallucination or improved
remediation require measured comparisons, including cases where no code change is
justified.
8.3 Continuous Integration and Workflow Automation
• Repository scanning and reviewed publishing are already described as configurable
capabilities. Future work should therefore focus on extending and validating them
rather than presenting them as entirely absent.
• Potential directions include policy-controlled continuous-integration initiation, clearer
review checkpoints and reliable comparison after changes.

• Publishing must retain explicit approval. Passing external checks must not
automatically resolve a finding. Deployment and permission constraints should be
tested in isolated repositories before broader use.
8.4 Scalability, Security and Deployment
• Further deployment work should evaluate queueing, worker isolation, concurrent
uploads, storage cleanup and recovery under load.
• Performance improvements must not weaken authorisation or omit checks without
disclosure. Operational evaluation should include provider outages, rate limits and
membership changes during active work.
• Browser-extension policy packs will also require version maintenance as store
requirements change. The objective is controlled and observable behaviour under
realistic conditions, not merely a lower duration from one benchmark run.
8.5 Extended Validation and User Studies
• The next research stage should use diverse, independently labelled projects and
participants with different levels of security experience.
• A user study could measure the time required to locate evidence, the ability to
distinguish suggestions from confirmed results, and the correctness of remediation
decisions.
• Participant consent and source confidentiality are necessary. These studies would
provide evidence about whether the integrated interface improves review work
rather than relying only on screenshots or developer impressions.
