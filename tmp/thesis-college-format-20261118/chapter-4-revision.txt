@349
ThreatLens was developed and reviewed in a Windows environment. The local development profile runs the browser application and Python API separately, with the browser handling interaction and the API handling audit requests. This arrangement made it possible to work on the audit flow without relying on every optional service in the worker-based profile.
@350
The installation notes describe Python 3.12 for the supported Windows setup and record a separate clean-install check with Python 3.12.14. That record helps reproduce the installation profile. It does not establish the exact Python version for every screenshot or audit in this thesis. The version used for a new run should be read from its active interpreter and saved with the run result.
@351
The machine specifications, browser build, and service versions were not recorded alongside every application capture. It would therefore be inappropriate to use those captures to infer resource requirements or compare execution speed. When a model request uses a remote provider, the local workstation also does not perform the model inference. Response times in that case may depend on network conditions and provider availability as well as the application.
@352
For a repeatable performance run, the environment record should include the operating system, processor, memory, browser version and the API profile. For a hosted worker, the record also needs the worker resources, concurrency and queue configuration. Versions should be recorded from the running processes where possible. A dependency declared in an installation file may not be the executable or package loaded by a particular process.
@354
The frontend uses TypeScript with React. TypeScript is useful at the point where API data becomes interface state: a pending scan, an audit with a saved finding, and a failed request need different rendering decisions. Static typing makes those distinctions visible during development, but still depends on checking inputs received at runtime. A typed response alone does not prove that access was authorised or that its contents are complete.
@355
The API and processing modules are written in Python, with FastAPI handling HTTP requests. Python also connects the archive, analysis, evidence and reporting stages. PostgreSQL stores persistent records, with schema changes maintained as SQL migrations. The boundary is intentional: transient progress belongs to the processing flow, while saved records should be available to an authorised user without restarting the scan.
@356
The declared dependency files and lockfiles provide the basis for a clean installation. To reproduce an evaluation, however, they should be tied to a source revision and an actual environment. Changes to rule packs, scanners, model settings or migrations can affect what a run produces even when the audit uses the same project archive. A comparison should capture these differences rather than describe both setups only by the application name.
@358
The browser client uses React 19, TanStack Router for routes and TanStack Query for server state. Routing allows the same selected audit to be opened from different views. The query layer helps keep server data separate from temporary interface state, such as a drawer being open. Tailwind CSS and shared interface components define the presentation; Monaco provides the read-only source view in the Workbench.
@359
Persistent information and interface state serve different purposes. The active audit reference can be used when a user returns to the Workbench, but evidence and access status still need to come from the server. Workspace-specific query keys help prevent a result fetched for one workspace from being displayed after another is selected. Source text is not needed in browser persistence to restore a reference to the audit.
@360
Interface verification should include more than an ideal desktop screenshot. Long paths, empty results, active jobs, loading failures and narrow screens exercise different parts of the layout. A source panel can scroll without altering the record it displays. Availability and readability can be observed in a browser, while server-authorisation behaviour requires separate checks with users who have different permissions.
@362
FastAPI exposes the intake and review operations used by the application. An audit request is checked before acceptance, and later requests retrieve progress, saved findings or available source evidence using the audit reference. Separating these requests prevents a slow processing stage from having to hold open the upload request for the entire scan. It also gives the interface a way to recover the current state after navigation.
@363
The backend applies validation at the boundaries where the frontend cannot be authoritative. In particular, workspace selection in the browser is an input to verify rather than proof of membership. Scan and finding identifiers have to refer to the same authorised workspace. A separate file lookup should also take account of the source preview's retention status instead of assuming that every saved finding still has an accessible file.
@364
Health endpoints and configuration checks are useful for deployment, but they answer narrow questions. A reachable API does not prove that authentication, storage access, optional model calls and report rendering all work. When these services are part of a demonstration, the record should identify which operations were actually exercised. An unavailable optional service should be reported with its effect on coverage, rather than described as an application-wide failure or a passed check.
@366
Supabase supplies authentication, the PostgreSQL database and private object storage. These services have separate roles: authentication identifies the signed-in account; database records hold workspaces, scans and findings; and private storage holds retained objects such as source previews. The Workbench connects those objects to saved metadata at the point of authorised access.
@367
PostgreSQL row-level security restricts which rows may be read or changed under a given policy [7]. Workspace membership is a useful basis for these decisions, but additional checks are needed when a server reads private storage or performs a privileged operation on behalf of a user. The trusted relationship is between the current user, workspace and specific saved record. It should not be derived solely from an identifier passed by the client.
@368
The project distinguishes owner, administrator, analyst and viewer roles. This allows read access to be separated from actions such as starting an audit or changing workspace configuration. Stored source previews have a configured 30-day retention window. A preview can therefore expire while its audit history and finding summaries remain. The data record should say whether code is still available instead of returning an empty excerpt as if the file had never contained evidence.
@370
Two processing modes are described in the project documentation. In the local profile, the API process coordinates the supported audit stages. This is the simpler path for development and for checking the browser-to-API workflow. In the full worker profile, background tasks are handled separately, with Celery and Redis providing task delivery. Figure 4.1 compares the modes in terms of where processing occurs.
@371
The profiles expose different operational questions. For the in-process path, interruption of the API process may affect an accepted job. For worker execution, a job can wait in the queue, be picked up by a worker or lose the worker while running. Both modes need a durable outcome that the browser can interpret. The queue's state, the worker's state and the saved audit state are related, but a signal from one is not always proof of the others.
@372
Qdrant is a supporting service in configurations with vector retrieval. It performs a different job from the task queue: it helps select reference material for later interpretation. Its inclusion in the full architecture does not mean that every installation retrieves documents or that it is needed for a static scan. The chapter therefore describes available components separately from the services evidenced by a particular run.
@375
The mode should be stated wherever it affects interpretation. The application captures establish user-visible behaviour, but do not record the process that performed every background step. For that reason, the figures do not serve as proof of worker execution, queue throughput or equivalence between the two deployment modes.
@377
The scanner profile determines which checks and supporting tools are available. The wider project includes static analysis, secret and dependency checks, and optional model assistance. A full installation may make specialist tools available that are absent from a smaller development profile. The useful record is the list of checks that actually ran, with the rules or advisory data they used, rather than the list of tools named in the architecture.
@378
Dependency analysis has a separate input boundary. The presence of a requirements or package file does not establish that exact installed versions are known. The supported Python audit path works with eligible exact package versions without installing uploaded dependencies. Unsupported inputs limit the review; they should not be interpreted as evidence that the associated components have no known issues. The same distinction applies when a scanner is not installed or a service is not configured.
@379
Model providers and retrieval services can contribute explanations and reference material when enabled. Their availability varies by profile and configuration. A reproducible run should record whether a model stage ran, which model or fallback served the request if known, and whether retrieval produced usable references. Documentation naming a provider cannot establish which service produced a particular saved answer.

Report generation introduces a further tool boundary. The application prepares the report content from saved records and uses a browser-based renderer for PDF output, with a fallback where the required dependencies are installed. A rendering check should record the actual engine used. The goal is to verify readable text, complete findings and consistent pagination, not simply to confirm that a file with a PDF extension was produced. The rendering engine does not take part in detection or choose which findings belong in the audit.
@381
The study uses application captures, project documentation, test records and technical references. The saved MERN application audit provides a case for examining reported findings and source coverage. An existing portal audit provides an example of the relationship between recorded evidence and contextual remediation. Neither project is treated as an independently labelled vulnerability dataset.
@382
The sources should be used for the questions they can answer. A screenshot shows a state presented to a user. A report records the saved findings and scope returned by the audit. A test log can show the outcome of a specified assertion. A standard or catalogue defines terminology and evaluation criteria. None of these, on its own, establishes the detection rate of the system against a collection of real projects.
@383
Reference data can change independently of the application. Tool rules, published advisories and compliance references may be updated between runs. The date or version used should be kept wherever the result depends on it, particularly when comparing a later run with older evidence. If a reference version is missing, that should be recorded as a limitation instead of assuming it matches the currently available material.
@385
For an audit to be repeated, a reviewer needs to be able to identify the source revision, input archive and processing profile. A compact record should include the archive checksum, selected frameworks, enabled stages and relevant versions. It should also distinguish the time at which evidence was captured from the time of the audit itself.
@386
Reproducibility does not require preserving credentials, private prompts or unrestricted copies of submitted code. A log can retain a scan reference, counts, status, duration and a sanitised failure category. A synthetic input or approved public fixture can be shared with a report where that is necessary to repeat the run. Private evidence should be restricted to the people and retention period agreed for its review.
@387
The project records provide a basis for repeating individual workflows, but not every field in this recommended record is available for older demonstrations. Chapter 6 identifies the claims affected by those gaps. Stating the missing information is more useful for future testing than assigning an exact configuration or result after the fact.

Version control and evaluation records should be connected without being confused. A source revision identifies what the team intended to run, while the evaluation record identifies the inputs, tools and configuration it actually used. A working copy may include local changes, and optional tools may be absent even on a clean checkout. For a later thesis experiment, the team should first record the revision and any relevant local changes, then save the enabled check list with the results. The archive checksum and a dated outcome record are enough to link those records without storing credentials in the research material.

It is also helpful to separate test materials by purpose. An input fixture belongs with its expected result and any permission to use it. A screenshot belongs with the capture date and the state it demonstrates. An exported report belongs with the scan reference and the filters used to produce it. When these records are stored together under an undated name, it is difficult to tell whether a difference represents a new run, a formatting change or an altered input. This separation is the reason that the saved application captures and the separate regression record are identified independently in Chapter 6.
