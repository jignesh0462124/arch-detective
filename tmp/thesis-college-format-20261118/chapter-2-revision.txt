@241
Vulnerability detection starts with a question about behaviour: can a weakness in the software cause a security failure under the conditions in which the software is used? A scanner can often point to the relevant operation before that question has been answered. The report may identify where a value is processed, for example, while leaving open where the value came from and whether a check ran before it reached that point. A developer reviewing the report needs both the observation and the context needed to interpret it.

A source location makes a finding easier to investigate. It also keeps the scope of the claim visible. A line that invokes a sensitive operation does not establish which users can reach it, how it is configured in production or what other parts of the application do before the call. One review may be able to settle those questions from the surrounding files. Another may have to leave them open because the deployment settings or the relevant code were not part of the submitted project.
@242
The methods in this chapter look at different parts of that problem. Source analysis can recognise a code pattern and, where the tool supports it, follow data between operations. A dependency check reasons from package identity and version information. A reviewer can consider who can reach a function and which business rules apply to it. These kinds of evidence belong side by side in an assessment, since one tool may answer a question that another never examined.
@243
A report with no findings is particularly easy to overread. For a reviewer, there is a practical difference between a file that was checked without a reported match and a file the tool could not analyse. There is also a difference between an alert that remains open and one the reviewer has examined and ruled out. Those distinctions shape the discussion that follows. They let us compare methods by what they examine and what they can support, without assuming that running several of them together improves accuracy.
@245
Static Application Security Testing (SAST) examines a program without running the target application. The OWASP Developer Guide describes techniques that apply rules, patterns or models to source or other representations of the program [1]. A pattern rule may record a particular call or expression. A check that works with a syntax tree can distinguish the role of that expression in the program instead of relying on the characters around it. Neither approach necessarily answers whether that part of the program will run in the deployment being reviewed.

Control-flow and data-flow methods address different questions. A control-flow analysis concerns the possible order of statements, such as whether a decision can bypass a check. A data-flow analysis asks how a value moves and changes as the program runs. A reviewer may need both accounts. The fact that a value could reach one statement in the source is less informative when the statement sits behind a condition that cannot be met in the relevant setting.
@246
OWASP uses taint analysis to describe the tracking of untrusted input from a source, through the operations that pass it on, to a sink where it is used [1]. For a developer, the useful part of that account is the path it makes visible. If a report records the sink but omits an intervening check, the reviewer needs to inspect that check before accepting the result. Likewise, a check designed for one context cannot be assumed to protect a different operation just because it runs earlier.
@247
The strength of a static finding depends on what the tool can see and what it knows about the code. A framework may route requests through a layer the tool does not model. Generated code or unresolved settings can hide pieces of the path. OWASP lists these gaps alongside the possibility of false positives and false negatives [1]. For ThreatLens, the design implication is to preserve the source location and any reported path or rule evidence, together with enough information to identify which checks ran. That gives the developer a place to start when a finding looks questionable.
@249
Dependency analysis, secret detection and configuration review each start with a different object. The dependency analyser examines the software packages a project uses. A secret detector looks for values that may grant access. A configuration check reads settings that influence how the application is built or deployed. Grouping their findings in one report is useful, but the reason for recording an alert should remain specific to the method that produced it.

For a dependency alert, a package name is only part of the evidence. A manifest may declare a range of acceptable versions, while a lock file records a particular resolution. If the submitted files only identify the range, the reviewer has to say what remains uncertain about the installed version. An advisory can establish that a version is affected; the project's dependency information establishes whether that version was selected. Whether the affected part of the package is in use is a separate question.
@250
Secret detection has a comparable uncertainty at the level of an individual value. A token-shaped string might be a credential, a placeholder in a sample file or a test value. A report should show enough context to explain why the value was flagged without copying it into a document that might be shared. A configuration warning has a different interpretation problem. A setting in an example file may never be loaded, or an environment-specific value may override it. The finding becomes useful when the reviewer knows which file supplied the evidence and whether that file governs the deployment under discussion.
@251
Basak and colleagues developed SecretBench as a labelled collection of candidate software secrets from public repositories [2]. They report 97,479 labelled candidates, of which 15,084 were classified as true secrets. Those counts describe their dataset. They are not findings produced by ThreatLens. What matters for the design of an evaluation is that a detector should face realistic look-alikes along with genuine cases. Testing only with conspicuous examples can show whether a rule will fire, but it cannot show how often it raises an unnecessary alert. The same reasoning supports keeping a scanner's unmatched or unassessed cases visible in the experimental account.
@253
The literature reviewed by Zhou and colleagues treats vulnerability detection and repair as distinct tasks [3]. A detection asks whether the available evidence supports a problem, while a repair proposes a change to address it. Their survey discusses prompt design, fine-tuning and retrieval among the ways researchers adapt language models to security tasks. It also examines which units of code are supplied and how datasets are constructed. Those details matter because the same model can be asked to classify an isolated function or to help a reviewer understand a finding that spans several files.
@254
For ThreatLens, the most immediate role of a model is to explain a saved finding and, when requested, suggest a change. The explanation can translate a concise scanner message into terms the developer can relate to the surrounding code. A useful response names the operation it observed and points to the recorded evidence. When it relies on a condition the supplied code does not establish, it should identify that condition explicitly. This is particularly important when only a short source excerpt is available.

Consider a reviewer who asks why an operation was flagged and receives a plausible account involving a call elsewhere in the project. The answer is useful if the reviewer can check that call in the submitted version. If the model was never shown the caller, the answer should be read as a possibility to investigate. Clarity helps the reviewer notice the difference; it does not make the missing source available.
@255
A repair suggestion raises a further question: does the change preserve the behaviour the application is meant to provide? A proposal may look reasonable in the selected excerpt and still interfere with a valid use case. Review therefore includes checking both the reported weakness and the ordinary behaviour around the affected code. A response that states its assumptions and gives a testable rationale is easier to assess than a patch with no explanation. The survey gives reasons to study this workflow, but it provides no measured accuracy for the particular models, prompts or provider configured for this project [3].
@257
Retrieval-augmented generation (RAG) gives a model access to reference material selected for the question at hand. In the work by Lewis and colleagues, a retriever searches an external collection and the generator uses the selected material when producing an answer [4]. The study evaluated knowledge-intensive language tasks. Its relevance here is the separation between the source of a reference and the text generated from it. Its results do not establish how a security review system will choose or interpret a control.
@258
For a security assessment, the passage supplied to the model might describe a weakness category or state a policy requirement. The description is useful when it helps the reviewer interpret the observed code. A paragraph that happens to use similar terms is not enough on its own. If the candidate passage covers a different version of a policy or a different kind of application, the model can cite it accurately while drawing the wrong conclusion about the project.

For example, a policy reference about what information must be disclosed may be relevant to a finding that involves data collection. The passage can explain the obligation. Whether the developer met it depends on the applicable version and on what was disclosed to users. That second part requires evidence from the project or its accompanying declarations. Retrieval helps locate the obligation; the underlying finding still has to carry evidence that the reviewer can inspect.
@259
The two steps suggest different evaluation questions. To examine retrieval, it is possible to ask whether the expected reference appears among the returned passages and whether the correct version was selected. To examine generation, the reviewer can ask whether the response uses the passage accurately and makes only claims warranted by the code and the reference. A satisfactory result in one step does not establish a satisfactory result in the other. Keeping the reference identity and its relationship to the finding makes both judgments possible.
@261
MITRE's Common Weakness Enumeration (CWE) provides names and identifiers for recurring types of weakness in software and hardware [5]. Using a shared identifier can help a reviewer compare findings that different tools describe in different words. The identifier describes a type of problem. Several locations can share one CWE without referring to the same defect, and a reviewer may need more evidence to choose the most appropriate category for a particular alert.
@262
The Common Vulnerability Scoring System (CVSS) is concerned with severity. The version cited in this thesis, CVSS v3.1, distinguishes Base metrics from Temporal and Environmental metrics [6]. The Base group captures technical characteristics of the vulnerability. Temporal metrics account for conditions that can change, and Environmental metrics can reflect the deployment where the issue matters. The vector records the metric choices behind a score. That record is useful when a reviewer wants to understand why two otherwise similar findings received different values.

A reviewer using a score to decide what to address first still needs local information. The importance of the affected application, the way it is exposed and the protections already in place can change what should be done first. FIRST describes CVSS as an input to that decision and identifies organisational considerations beyond the score [6]. A missing score should be left as unavailable rather than interpreted as a severity of zero.
@263
Classification, severity and review status should therefore remain separate fields. The weakness label answers what kind of issue the report describes. The severity indicates the potential seriousness under the recorded assumptions. A status such as open tells the team where the finding is in its review process. A control reference can be displayed alongside these fields, but it answers a different question about a requirement. If the fields were collapsed into a single indicator, the reviewer could not tell whether an item changed because of new evidence, a revised score or a decision about how to handle it.
@265
Compliance mapping begins with an observation and a specific requirement. The mapping has to explain the connection. A source file might show that a setting is present, but it may not show who is responsible for it, when it is checked or whether it is active in another environment. Recording the relevant requirement is useful because it tells the reviewer what to check next. A stronger conclusion needs evidence that covers the rest of the requirement.
@266
The gap is most visible with obligations that concern organisational practice. A repository can contain a policy configuration without documenting how exceptions are approved or whether the procedure is followed. In a package review, a developer's declaration and the material shown to users may be necessary evidence. Where those details are absent, classifying the matter as requiring review is more informative than treating it as a pass or assuming a violation. It also lets a report remain useful after the initial assessment, since the reviewer knows what material would resolve the open question.
@267
Remediation guidance should name the assumption behind the proposed change and identify the behaviour to check after applying it. For a setting, a reviewer might compare the value in the submitted file with the value actually used in an authorised test environment. For a source change, the check should cover the reported condition and the normal behaviour the original code supported. A successful review of a proposal shows that it is suitable for testing. It does not show that it was merged, deployed or confirmed to resolve the finding. ThreatLens presents the guidance with that boundary in mind.
@269
The comparison here is between assessment methods. A tool can do well at identifying what is in a submitted project and still be poorly placed to answer what happens in a deployed environment. Comparing tools by the number of alerts they produce would miss that difference. The useful questions are what each method needs as input, what evidence it returns and what work remains before a reviewer can act.
@270
A source rule can point to a file and an operation that merit inspection. A dependency tool can link a recorded package version to an advisory. Secret and configuration checks direct attention to a possible credential or a relevant setting. A model can give those observations a readable explanation, while a human reviewer can check the assumptions against application behaviour. Figure 2.1 locates the point where these forms of evidence meet. It does not show that each method contributes equally to every case.
@271
Consider an audit in which a dependency warning appears beside a separate source finding. The dependency warning has to be reviewed against the installed package version and its use in the project. The source finding has to be reviewed against the recorded code and the conditions under which it runs. They may lead to different actions, even when both are assigned the same severity. The point of presenting them in one place is to make the evidence easier to compare, rather than to imply that the two checks had the same coverage or confidence.
@274
An interface comparison can show how easily a reviewer can locate the supporting evidence or find a recorded decision. A performance comparison needs common inputs, the same matching rules and a definition of what counts as a correct finding. It also needs to account for work the baseline did not perform. A shorter run that skipped part of the input is not evidence of a faster check over the same scope.
@276
The cited sources address different parts of a review. OWASP explains what a static tool can observe and why its findings need interpretation [1]. SecretBench shows the value of retaining false-alarm candidates when constructing an evaluation dataset [2]. Zhou and colleagues examine how models are used for detection and repair and why the choice of input and evaluation data matters [3]. The three sources are useful at different points: when deciding what evidence to retain from a scanner, when planning a test set and when deciding what a generated response needs to explain.
@277
Lewis and colleagues provide a basis for coupling an answer with retrieved text [4]. CWE and CVSS provide terminology against which classification and severity can be described consistently [5, 6]. None of these references tells the reviewer whether a particular mapping applies to the submitted project. That judgment depends on the project evidence and whether it satisfies the conditions stated in the reference. The role of the system is to carry the source and the reference into the same review without losing the distinction.
@278
This synthesis gives us two practical design criteria. Each finding needs an identifiable origin so it can be reopened and checked. Its explanation should state which assertions follow from the evidence and which remain open. These criteria can be assessed even if a broad detection benchmark is not available. Testing them can establish whether the application preserves a usable review trail. A claim about the accuracy of the combined system requires further evidence about the defects it finds and misses.
@280
The gap addressed in this thesis lies in the handoff between a tool observation and the reviewer's decision. A finding may move through a source view, a classification, a suggested control and a report. At each point the reviewer needs to recognise the original observation and see any assumptions introduced later. A system can produce technically valid output at each step, yet still leave an unclear assessment if the evidence stops being traceable between those views.
@281
The difference is visible when a saved report is reopened. If source is no longer available, the report should still distinguish a retained observation from a claim that would need a fresh inspection to verify. If a rule failed or an input could not be assessed, the report needs to communicate that lost coverage. An evaluation of the workflow can reproduce these cases and examine whether the presentation remains accurate. Such tests answer questions about continuity and reliability, not about overall detection accuracy.
@282
The methodology in Chapter 3 follows from this division. Evidence continuity can be examined by tracing a known finding from its original location to the saved report. Coverage can be examined by recording which material was included, excluded or unavailable. Detection performance needs independently labelled cases and a repeatable comparison. Usability and operational behaviour also need measures that fit their own questions. Taken separately, those checks allow the study to say which parts of ThreatLens have been evaluated and where additional evidence is still needed.
