@151
Software applications handle personal information and business transactions. They also carry messages and give people access to essential services. A decision made while writing a single part of an application, such as where to check a permission or how to store a sensitive value, can affect all the users who depend on it. Input validation and database query construction are similarly easy to overlook when the immediate goal is to make a feature work. Security review belongs in the development process while there is still time to inspect and change those decisions. The National Institute of Standards and Technology (NIST) makes this point in its Secure Software Development Framework, which places security practices throughout the software development life cycle. [[CITES]]
@152
As a project grows, the work of checking a warning is seldom confined to the line named in the alert. The developer may need to follow a value from the file in which it arrives to the file in which it is used. A framework may handle one step, while a library or a local helper handles another. The review then becomes a question of which checks are already in place and what would happen if the proposed correction changed the way the application behaves.

Consider an ordinary review after a change to an account page. A developer receives a warning and opens the affected file. To decide whether to act, they need the original location, enough surrounding code to understand it and a clear account of what the warning means. If the finding is still open when another developer returns to the audit, those details should be available without reconstructing the investigation from memory. This is the part of source review that motivates ThreatLens.
@153
Static Application Security Testing (SAST) examines source without running the application. It can point a reviewer towards code worth checking, including unsafe output handling, injection-prone operations and possible exposure of credentials. The reported line is where the investigation starts. A rule can raise an alert for code that is safe in context, and it can miss behaviour that depends on application state or business rules. The reviewer still has to look at the code before classifying the issue. [[CITES]]
@154
A language model can explain an unfamiliar operation or draft a possible remedy. That help is useful when a scanner has identified a concrete issue but its message leaves the developer unsure what to change. The explanation may also make assumptions about code the model has not seen. NIST describes plausible, unsupported model output as confabulation and recommends evaluating generated output and checking the sources that support it. In an audit, that means keeping each generated explanation beside the evidence it discusses so a reviewer can check the two against one another. [[CITES]]
@155
We developed ThreatLens to support review from the time a project is submitted to the time a finding is revisited or reported. A developer can follow the progress of an analysis, open a saved finding and inspect the available source before deciding on the next step. The purpose of the workflow is to make that decision easier to trace. The decision itself still belongs to the reviewer.
@157
An automated warning has practical value when a developer can connect it to a specific part of the application. A category name alone cannot tell the reviewer which statement caused the warning or whether it matters in the conditions where the software runs. Before proposing a fix, the reviewer needs to establish whether input can reach the recorded operation and whether a check elsewhere already prevents the unsafe case. A useful finding supplies the location and evidence for that investigation.
@158
An HTML update provides a simple example. Assigning a fixed, trusted value and assigning a value that an outside user can influence require different conclusions, even when both uses appear on the same kind of line. The recorded evidence can establish that the update occurs. It may leave the origin of the value or the surrounding protections unclear. In that situation, asking the developer to check the value and its path is more useful than presenting the warning as confirmed cross-site scripting or promising that a replacement will fix it.

The same distinction affects remediation. A change may address the operation a scanner recognised while failing to address the actual source of the problem. It may also alter a legitimate part of the interface. A proposed remedy is easier to assess when it says what behaviour must stay the same and which checks would show that the change is acceptable.
@159
Reviewers also need a way to decide what to look at first. The Common Vulnerability Scoring System (CVSS) describes technical severity. FIRST treats that score as one input to vulnerability management, where the organisation and its environment still matter. A high score can justify earlier review, but a developer still needs to know whether the affected function is available in their deployment and what the application depends on it for. ThreatLens therefore presents severity as a property of the finding and leaves the decision about operational priority to the reviewer. [[CITES]]
@160
A review system has to show what happened when an audit could not run to completion. Uploaded archives are untrusted, and recovery from a failure must not make a partially analysed project appear clean. The source preview may be preparing while analysis runs. An external service may be unavailable. A developer may leave the page and return to the audit later. Each condition calls for a different explanation because it leaves a different amount of evidence available to the reviewer.

For instance, an accepted upload means the service received and recorded the submission. It does not mean that every check ran or that the result is ready. If a preview later expires, the report may still be available. The interface should make clear that the evidence is limited by the expired preview rather than suggesting that the finding has disappeared.
@161
The problem addressed here is how to connect automated checks to a review process that people can understand and repeat. ThreatLens needs to keep each finding tied to the evidence that produced it, offer remediation that can be checked and restrict private material to the people authorised to see it. The resulting audit should tell the reader what the system assessed and where its assessment stopped.
@163
In a manual review, the reviewer can ask whether a piece of code behaves as the application intended and whether it follows the business rules that apply to it. That context is especially useful when a general scanner rule would make little sense on its own. Manual review depends on the time and experience available, though. Two reviewers may also follow different paths through a large project unless the scope and the evidence they inspected are recorded.
@164
Rule-based scanners help with checks that can be repeated over the same files. Different scanners can describe the same underlying condition using different names or point to different parts of it. Conversely, the same rule can identify separate occurrences that need separate review. Consolidation has to keep enough information to tell these cases apart. If a result is combined with another one, the reviewer should still be able to see where the original evidence came from.
@165
A conversational assistant can explain a finding in terms familiar to the developer. An answer given without the exact source version may fit a similar-looking example and still be wrong for the saved audit. In ThreatLens, finding-specific guidance uses the evidence available to the authorised reviewer. The suggestion appears separately from the uploaded source so an example can be read without assuming that it is part of the original code.
@166
Some compliance questions cannot be answered from source alone. Chrome Web Store policies cover the extension and the way it is presented, including declarations and marketing materials. Microsoft Edge Add-ons policies also consider matters such as permissions, privacy, functionality and changes to browser settings. A built extension ZIP can show what is in the package or which permissions the extension requests. It may not tell the reviewer what the developer disclosed or whether the user saw an appropriate explanation. Those questions may require a declaration or a manual check. [[CITES]]
@167
The same record can therefore contain several kinds of information. A scanner alert records an observation. A suggested control mapping gives the reviewer a policy to consider. A model response may explain either item, and a reviewer can record a decision separately. Keeping these entries distinct lets a reader see what was measured, what was suggested and what still needs evidence.
@169
The research gap addressed by this thesis is how automated results can be carried into an assessment that remains traceable as the reviewer moves between views and returns to a saved audit. Tools already exist for parts of that work. This study examines their integration within ThreatLens and asks what evidence would show that the integrated workflow behaves as intended.
@170
The first issue is continuity of evidence. A developer should be able to open a finding in the Audit Workbench, select it again in Findings, and recognise the same record in the Attack Graph, Security Advisor and Reports. The title of a finding may be shared by more than one occurrence, so a title is a poor substitute for its audit, file location and recorded evidence. Each view can serve a different purpose while still making it clear which finding is under review.

That requirement becomes more important when a view is filtered or only some records have loaded. A count can be accurate for the view shown and still differ from the saved audit total. The interface needs to say which count it presents. An evidence link should likewise keep its original audit and location, even when the source excerpt is temporarily unavailable.
@171
The second issue is how to interpret remediation guidance. A reviewer should be able to see which part of a suggestion comes from the evidence and which part depends on an assumption about the application. The proposed change must remain separate from the original code. Its status should also be clear: generating a suggestion shows that the system produced a response, while applying a change and checking it are separate actions.
@172
The third issue is how to assess coverage and correctness. A completed job means the scan reached its end state. It may still leave files, vulnerability classes or policy requirements outside the assessment. Evaluation therefore needs to identify the input that was eligible, the evidence saved, and the checks the system did not perform. Access isolation and consistent reporting can be tested with known cases. Detection accuracy requires a different comparison against independent labels.
@173
These issues define what the integration has to demonstrate. The implementation can be examined through known workflows and their saved evidence. A claim that the combined system detects more vulnerabilities than another method would require a controlled comparison beyond that implementation check.

The work starts from recorded source evidence and gives developers a way to inspect a finding before deciding whether to act on it.

@187
The project addresses four research questions.
@192
The four questions call for different kinds of evidence. The first two can be investigated by following known findings from analysis into the Workbench and checking which source evidence remains available. The third calls for a review of policies with different evidence requirements, such as a check the package can answer and one that still needs a developer declaration. The fourth concerns how the system behaves when access changes, processing is incomplete or source is no longer available.

Repeatable tests can establish whether the workflow handles those cases consistently. They cannot establish precision or recall unless the expected results were independently labelled and a procedure was set for matching findings to those labels. In the same way, a screenshot can show what is available on a page, but a usability study would be needed to tell whether reviewers can interpret it reliably.
@194
The main workflow covers submitted source projects and saved audit results. A developer supplies a project ZIP, and the service prepares source previews as they become available. Recorded findings can then be examined in the read-only Workbench. Related views support filtering, triage, evidence relationships, contextual guidance and report downloads. Repository features depend on the required GitHub setup and the permissions of the person using them.
@195
ThreatLens also reviews built ZIP packages intended for the Chrome Web Store or Microsoft Edge Add-ons. The review compares available package evidence and supplied declarations with versioned policy references. It distinguishes violations detected by the checks from requirements that need human review, remain unassessed or do not apply. ThreatLens does not install the extension, inspect the developer's browser settings or submit the package to a store.

The extension package illustrates a wider limit of the project. A package may contain enough information to compare a declared permission with a policy. A separate requirement may depend on behaviour or information outside that package. If the reviewer cannot obtain that evidence, an unassessed status conveys more than a pass would. The store makes its own approval decision.
@196
Assessment is bounded by the source that is available, the supported analysis methods, the input limits and the services configured for the run. Static checks do not reproduce every runtime condition or establish that the application follows every business rule. Model explanations can also be wrong. A report with no recorded findings shows what the completed assessment recorded for the supplied input. It cannot rule out weaknesses outside that coverage.
@197
Remediation suggestions require review and testing. When repository publishing is configured, an authorised user can review a diff and publish it through a separate branch and pull request. The workflow does not change the target branch automatically. A proposed change, a structural validation check and an open pull request each provide a different record of progress. None establishes on its own that the original finding has been resolved.
@198
Project information is restricted through authenticated workspace access and private source storage. Source previews are available for a defined period. Saved findings and reports have their own history, so a reviewer may be able to revisit the audit after the preview has expired. Where the deployment uses an external model service, service availability and the way the configuration handles submitted material also need to be considered when projects are selected for assessment.

These limits matter when interpreting results. A past report can establish what the system recorded at the time of the audit. If its underlying preview is no longer available, the report cannot substitute for the original source when a reviewer needs to test a detailed explanation. That follow-up may require a new audit of an authorised copy of the project.
@200
Figure 1.1 shows the components used in the audit workflow. The application sends authorised requests to the API. Source preparation and analysis may progress independently, and the resulting records make it possible to revisit an assessment from another page. The contributions below concern the workflow built around those records.
@204
ThreatLens brings project submission, analysis progress, source review, finding management and reporting into the same application. An audit reference lets a developer return to a saved result without having to remain on the page that started the scan. This is useful when one person starts the audit and another authorised member reviews it later.
@206
The Audit Workbench places the file tree, read-only source viewer and finding details together. A developer can compare the explanation with the recorded line and its surrounding context without leaving the audit. The workbench is for inspection; its source display is separate from the process of changing a repository.
@208
The interface separates written remediation from a requested code suggestion. When a code solution is generated, it can include the assessment, the proposed code, the assumptions behind it and suggested verification steps. An interrupted response stays identifiable as incomplete. This lets the reviewer decide whether the available guidance is sufficient even when a model response did not finish.
@210
Findings, the graph and reports refer back to saved audit information. The graph can show which components or locations are associated with recorded findings. Its connections are evidence relationships. A reviewer would need independent runtime evidence before describing one as an attack path that was actually used.
@212
The extension workflow uses separate policy references for Chrome and Edge. It combines evidence from the built package with the developer's declarations and shows where manual review is still needed. A corrected package can be reviewed as a new audit. Comparisons are useful where the review settings and coverage are compatible; otherwise a changed result also needs to be interpreted in light of the checks that ran.
@214
Documented checks address access isolation, scan state handling, source availability, report completeness and interface responsiveness. These checks are useful when they reproduce a situation a reviewer would encounter. For example, a test that reopens a saved scan checks whether the workflow retains the result. It says nothing about how many vulnerabilities the detector missed.
@215
The contribution of this work is the way the system connects those review functions and records the evidence available at each step. ThreatLens uses language models as part of that workflow and relies on a reviewer to decide which findings and suggestions are supported.
