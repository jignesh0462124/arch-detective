ABSTRACT
Security assessment is often treated as a separate activity from software
development. Developers may receive vulnerability reports that identify a problem but
provide little context about the affected code, its potential impact, or the steps needed to
address it. Compliance requirements add another challenge, particularly when technical
findings must be connected to documented controls or browser-extension store policies.
These gaps make security review difficult to interpret and act upon, especially for small
development teams.
This thesis presents ThreatLens, a web-based platform that brings codebase auditing,
threat modeling, compliance assessment, and remediation guidance into a single
workflow. Users can submit project archives for analysis and examine saved results
through a read-only, editor-style workbench. The platform combines static security checks
with language-model-assisted analysis to identify potential weaknesses and provide
explanations grounded in available source evidence. Findings include severity, recorded
file locations, relevant code excerpts, and remediation guidance.
The workbench connects source files with findings, control mappings, and suggested
verification steps. An evidence-based graph helps users explore relationships between
findings and affected components without presenting those relationships as confirmed
exploitation paths. Security Advisor provides contextual explanations and code
suggestions, while keeping proposed changes separate from the uploaded source.
Browser-extension reviews extend this workflow to Chrome Web Store and Microsoft
Edge Add-ons policies, distinguishing detected violations from requirements that need
manual review or cannot be assessed from the submitted package.
ThreatLens also provides saved audit history, finding triage, comparison of compatible
extension reviews, and downloadable reports. Workspace authorization, private source
storage, evidence redaction, and time-limited source previews support controlled access
to sensitive project information. Verification covers automated regressions, access-
control checks, report generation, and representative browser workflows; these checks
establish functional behavior rather than proving universal vulnerability-detection
accuracy.
The principal contribution is an integrated, traceable review workflow that helps
developers move from a reported concern to its supporting evidence, possible remedy,
and verification approach. ThreatLens supports informed security decisions, but does not
replace manual testing, professional assessment, or official compliance and store-
approval processes.
Keywords: Codebase Security Auditing; Static Analysis; Threat Modeling; Compliance Assessment;
Large Language Models; Secure Software Development.

CHAPTER 1 INTRODUCTION
1.1 Background and Motivation
Software applications manage personal information, business transactions,
communication and access to essential services. Their security depends partly on
decisions made during development, including how inputs are validated, database queries
are constructed, permissions are enforced and sensitive information is stored. A weakness
in these areas can expose information or allow unintended operations. Security
assessment must therefore form part of software development rather than being treated
only as a final check before deployment. The Secure Software Development Framework
published by the National Institute of Standards and Technology (NIST) supports
integrating security practices throughout the software development life cycle. [1]
Reviewing source code becomes more demanding as projects grow across multiple files,
frameworks and dependencies. A developer investigating a warning may need to locate
the affected statement, understand the surrounding code and determine whether the
reported condition is relevant to the application. Finding a potentially unsafe operation is
only one part of this process. The reviewer must also decide what evidence supports the
finding and how a proposed correction can be checked without changing the intended
behaviour.
Static Application Security Testing helps identify suspicious code patterns without running
the application. It provides a useful starting point for reviewing concerns such as injection,
unsafe output handling and exposed credentials. However, a reported pattern is not
necessarily an exploitable vulnerability. Static analysis can produce false positives and
may miss problems that depend on runtime conditions, application state or business logic.
Its results therefore require interpretation and verification. [2]
Language models offer another form of assistance by explaining code and suggesting
possible remedies. These capabilities are useful when a finding is technically correct but
difficult for a developer to understand. Nevertheless, generated explanations can contain
incorrect assumptions or plausible but unsupported statements. NIST identifies this risk as
confabulation and recommends evaluating generated outputs and verifying their
supporting sources. In security assessment, a convincing explanation must not be
mistaken for verified evidence. [3]
ThreatLens is motivated by the need to connect these activities within a practical review
environment. It brings project submission, automated analysis, source inspection, finding
review, remediation guidance and reporting into one workflow. Its purpose is to help

developers understand what was reported, examine the available evidence and decide
what to investigate next. Human review remains necessary throughout this process.
1.2 Problem Statement
An automated security finding is useful only when the developer can relate it to the
application being reviewed. A warning that names a vulnerability category without
showing its source location or supporting evidence leaves important questions
unanswered. The developer still needs to establish whether the affected code receives
untrusted input, whether relevant safeguards exist and whether the reported operation
can be reached under realistic conditions.
For example, the presence of a potentially dangerous HTML operation does not, by itself,
demonstrate cross-site scripting. The interpretation changes depending on whether the
assigned content is a fixed, trusted value or contains attacker-controlled data. A useful
assessment should distinguish the observed operation from assumptions about input
control and runtime behaviour. Otherwise, an automated warning may lead to
unnecessary changes or distract attention from a more significant issue.
Prioritisation introduces a related difficulty. Severity labels and Common Vulnerability
Scoring System scores help communicate technical characteristics, but they do not
independently establish the operational importance of every finding. FIRST describes CVSS
as a severity framework and notes that vulnerability management also requires
organisational and environmental considerations. ThreatLens must therefore present
available severity information without implying that a numerical score proves exploitation
or completely describes business risk. [4]
The review process also has practical reliability requirements. Uploaded archives are
untrusted inputs. Source previews may still be preparing while analysis continues, and
external services may become unavailable. Users may leave a page before a scan finishes
or reopen an audit after its source-preview window expires. These conditions must be
explained accurately. An incomplete scan must not appear clean, and an unavailable
preview must not erase saved findings.
The problem addressed by this project is therefore to develop a source-code assessment
platform that combines automated checks with understandable, traceable review. The
platform must preserve the relationship between a finding and its evidence, provide
useful remediation guidance, control access to private project data and make analysis
limitations visible. It must support investigation without presenting automated output as
a guarantee that an application is secure.

1.3 Existing Approaches and Challenges
Manual code review allows a reviewer to consider application purpose, expected
behaviour and business rules. It is valuable where security depends on context that is
difficult to express through a general rule. Its effectiveness, however, depends on
reviewer knowledge, available time and familiarity with the project. Maintaining
consistent review coverage across a growing codebase can be difficult.
Rule-based scanners provide repeatable checks for defined patterns. Their output can
help reviewers focus on relevant files, but different tools may describe similar issues using
different categories or evidence formats. Bringing those results together requires more
than displaying them in one list. The system must preserve distinct findings, handle
genuine duplicates and retain the information needed to understand where each result
originated.
Conversational assistants can help explain a finding, but a general conversation may not
include the exact source version, saved evidence or application context. A response can
consequently recommend a change that does not match the recorded problem.
ThreatLens addresses this concern by linking finding-specific guidance to authorised audit
context and keeping suggested replacement code separate from recorded evidence.
Compliance review adds requirements that cannot always be inferred from source code.
Browser extensions illustrate this distinction clearly. Chrome Web Store policies apply to
the wider extension experience, including declarations and marketing materials. Microsoft
Edge Add-ons policies also address matters such as permissions, privacy, functionality and
browser-setting changes. A packaged ZIP can provide evidence for some checks, while
other requirements need developer declarations or manual assessment. [5] [6]
These approaches serve different purposes. The challenge for ThreatLens is to connect
them without hiding their differences. A scanner result, a model-generated suggestion, a
compliance mapping and a reviewer decision should remain distinguishable even when
they appear in the same interface.
1.4 Research Gap
This study addresses an integration and evaluation gap: how to connect automated
security results with a review process that remains understandable, traceable and
appropriately bounded. The work does not assume that existing scanners or development
platforms lack all such capabilities. Instead, it examines how these requirements can be
implemented together within ThreatLens and verified against the project’s intended
workflows.
3

PAGE 16
The first area concerns evidence continuity. A finding should remain connected to its
audit, file location and available source excerpt as the user moves between the
Workbench, Findings, Attack Graph, Security Advisor and Reports. If these views show
inconsistent counts or disconnected details, the reviewer may struggle to determine
which result is authoritative. Maintaining this continuity is therefore a system
requirement as well as an interface concern.
The second area concerns the interpretation of remediation guidance. An explanation
should make clear what was observed, what remains uncertain and why a suggested
change may be relevant. Generated code also needs to remain visibly separate from the
original source. Producing a suggestion must not imply that the change has been applied,
tested or proven to remove the underlying issue.
The third area concerns coverage and evaluation. Completing an analysis job does not
establish that every file, vulnerability class or policy requirement was assessed. Similarly,
functional tests do not demonstrate universal detection accuracy. ThreatLens therefore
needs explicit coverage information and an evaluation approach that separates workflow
correctness, access control, evidence consistency and detection quality.
The research gap addressed by the thesis is consequently the practical design and
verification of an integrated assessment workflow with these distinctions intact. Its
contribution is evaluated through the implemented system and supporting evidence,
rather than through an unsupported claim that combining existing tools automatically
produces superior security results.
1.5 Aim and Objectives
The aim of this project is to develop and evaluate ThreatLens as an AI-assisted framework
for automated source-code security assessment, vulnerability prioritisation and
compliance analysis, with source-based evidence and human review at the centre of the
workflow.
The project objectives are:
1. To provide an authenticated project-submission workflow that validates supported
inputs and prepares source material for assessment.
2. To combine static security checks with language-model-assisted analysis while
retaining finding provenance and relevant source evidence.
3. To organise findings into a consistent representation that supports file locations,
vulnerability categories, available severity information and review status.
4. To develop a read-only Audit Workbench through which users can inspect source
files, findings, remediation steps and suggested verification activities.
5. To provide contextual explanations and on-demand code suggestions that remain
separate from uploaded source and require review before use.
4

PAGE 17
6. To present evidence relationships and applicable compliance mappings without
treating them as confirmed attack paths or proof of compliance.
7. To support saved audit history, controlled access, report generation and the
reopening of results across the audit lifecycle.
8. To evaluate functional behaviour, evidence consistency, access restrictions, failure
handling and interface responsiveness using documented test cases and
appropriate fixtures.
Together, these objectives establish a sequence from safe submission to evidence-based
review and reporting. They do not include unrestricted execution of uploaded projects,
autonomous acceptance of generated fixes or guaranteed detection of every
vulnerability.
1.6 Research Questions
The study is guided by the following research questions.
RQ1. How can static security checks and language-model-assisted analysis be combined
while preserving the source location, provenance and supporting evidence of each
finding?
RQ2. How can an editor-style workbench present findings, severity information and
remediation guidance so that users can distinguish recorded facts from assumptions and
generated suggestions?
RQ3. How can security findings and compliance assessments be presented together
without confusing vulnerability severity, policy outcomes and unassessed requirements?
RQ4. How reliably does the implemented workflow handle authorised access, incomplete
scans, unavailable services, source expiry and the reopening of saved results?
These questions guide both implementation and evaluation. Evidence consistency and
workflow behaviour can be examined through repeatable tests. Claims about detection
precision or recall require independently labelled examples and a defined assessment
procedure. Interface usability also requires suitable evaluation; the presence of a feature
alone does not establish that users find it understandable.
1.7 Project Scope and Limitations
ThreatLens focuses on the assessment of submitted source projects and the review of
saved results. The main workflow accepts project ZIP archives, prepares available source
previews and presents recorded findings through a read-only workbench. Supporting
pages provide finding filters, triage, evidence relationships, contextual guidance and
5

PAGE 18
report downloads. Repository-related capabilities depend on the required GitHub
configuration and the acting user’s permissions.
The project also supports review of built browser-extension ZIPs for Chrome Web Store
and Microsoft Edge Add-ons. This review considers package evidence and supplied
declarations against versioned policy references. It distinguishes detected violations from
checks that need manual review, remain unassessed or are not applicable. The platform
does not install extensions, inspect the developer’s actual browser settings or submit
packages to either store.
Assessment is limited by the available source, supported analysis methods, input limits
and configured services. Static review cannot establish every runtime condition or
business-logic requirement. Model-assisted explanations may also contain mistakes. A
report with no recorded findings therefore describes the outcome of the performed
assessment, not proof that the project contains no security weaknesses.
Remediation suggestions remain subject to review and testing. For configured repository
workflows, publishing follows a reviewed branch-and-pull-request process rather than an
automatic change to the target branch. Creating a proposal, passing a structural check or
opening a pull request does not independently establish that a finding has been resolved.
Project information is handled through authenticated workspace access and private
source storage. Source previews follow a defined retention window, while saved findings
and reports have separate history behaviour. Where external model services are used,
their availability and data-handling configuration form part of the deployment boundary.
These constraints must be considered when selecting projects for assessment and
interpreting the results.

CHAPTER 2 LITERATURE REVIEW
2.1 Introduction to Software Vulnerability Detection
Vulnerability detection attempts to identify conditions that may allow software to behave
insecurely. A useful assessment distinguishes a suspicious construct from a demonstrated
vulnerability. The meaning of an alert depends on data flow, validation, configuration and
runtime conditions.
Different analysis methods provide different forms of evidence. Some recognise known
patterns, while others reason about dependencies, source relationships or likely
behaviour. Human review remains important because an automated tool may not have
enough information to determine whether a reported condition is reachable or
exploitable.
This chapter considers these complementary methods and their relevance to ThreatLens.
It does not assume that combining several tools automatically improves detection
accuracy.
2.2 Static Application Security Testing (SAST)
Static analysis examines code without running the target application. Depending on the
tool, it may use pattern matching, syntax trees, control-flow analysis or data-flow
reasoning.
OWASP describes taint analysis as following untrusted data from a source towards a
potentially dangerous sink [1]. This helps reviewers understand whether external input
can reach a sensitive operation without appropriate handling.
The usefulness of static analysis depends on the supported language, rules and available
context. Framework-specific behaviour, dynamic execution and incomplete source
information can limit the analysis. A reported pattern should therefore lead to
investigation rather than an automatic claim that exploitation is possible.
2.3 Dependency, Secret and Configuration Analysis
Dependency analysis examines the packages used by an application and their recorded
versions. Secret detection looks for credentials or similar sensitive values. Configuration
analysis examines settings that influence deployment and application behaviour.
10

PAGE 23
These tasks require different evidence. A package finding needs reliable version
information, whereas a suspected secret requires contextual interpretation. A token-
shaped string may be a placeholder, a test value or a genuine credential.
SecretBench provides a labelled dataset intended to support research on software-secret
detection [2]. Its methodological relevance is that evaluation requires both genuine
examples and misleading look-alike values. A collection containing only successful
detections cannot adequately measure false alarms.
2.4 AI and Large Language Models for Code Security
Language models can relate a code fragment to a natural-language explanation and
suggest possible changes. Zhou and colleagues review research on their use in
vulnerability detection and repair [3].
This literature provides a foundation for exploring model-assisted review, but it does not
establish the accuracy of the provider, model or prompts selected for ThreatLens.
Generated explanations must be checked against the submitted source.
The need for review becomes particularly important when the model receives only part of
a file or lacks runtime context. A convincing explanation may still overstate the evidence,
misunderstand an application-specific assumption or propose a change that alters
intended behaviour.
2.5 Retrieval-Augmented Generation in Security Analysis
Retrieval-augmented generation combines generated responses with retrieved reference
material. Lewis and colleagues describe an approach that incorporates an external
retrieval mechanism into knowledge-intensive language tasks [4].
In security review, reference material may include weakness descriptions, secure-
development guidance or control clauses. Retrieved passages can help explain why a
finding may relate to a particular requirement.
However, finding a relevant passage and interpreting it correctly are separate tasks.
Retrieval supplies context; it does not independently verify a vulnerability or settle a
compliance question. The reference source and the reasoning behind each proposed
relationship must remain available for inspection.
11

PAGE 24
2.6 Vulnerability Taxonomies and CVSS Prioritization
MITRE’s Common Weakness Enumeration provides a vocabulary for describing categories
of software and hardware weaknesses [5]. It helps organise findings using consistent
terminology.
The Common Vulnerability Scoring System serves a different purpose. CVSS characterises
vulnerability severity through defined metrics [6]. A weakness identifier is not a severity
score, and neither is a triage decision.
Keeping these concepts separate prevents misleading interpretations. A critical severity
label describes potential seriousness under stated assumptions. An open status describes
the current review state. A control mapping describes a possible relationship to a
requirement. These fields should not be treated as interchangeable.
2.7 Compliance Mapping and Remediation Guidance
Compliance mapping links an observation to a potentially relevant requirement. A useful
mapping explains why the requirement applies and identifies any supporting evidence
that is still missing.
Many obligations concern organisational procedures, staff responsibilities or operational
controls that cannot be established from a repository alone. Source inspection can
support part of an assessment, but it cannot demonstrate every aspect of compliance.
Remediation guidance has a similar limitation. A recommendation should identify its
assumptions, expected behavioural effects and suggested verification steps. ThreatLens
treats both mapping and remediation as assistance for a reviewer rather than a substitute
for professional assessment.
2.8 Comparison with Existing Security Assessment Tools
The comparison in this study is organised by method rather than unsupported product
rankings.
Static analysis contributes repeatable rule-based checks. Dependency and secret tools
provide specialised inspection. Model-assisted review contributes explanations and
contextual reasoning. Manual review contributes application knowledge and judgement.
These roles overlap, but they are not interchangeable. ThreatLens is considered as a
workflow that combines and presents evidence. Claims of better precision, recall or
performance require controlled baseline experiments rather than a comparison of
interface features.

The selected sources address different levels of the problem. OWASP explains analysis

3.10 Evaluation Metrics
Detection quality is measured using independently labelled reference cases.
Let:
• TP represent correctly identified labelled defects.
• FP represent incorrectly reported defects.
• FN represent labelled defects that were missed.
The metrics are:
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1-score = 2TP / (2TP + FP + FN)
A zero denominator should be handled using a stated convention rather than silently
treated as a perfect result.
Timing metrics should distinguish acceptance-to-first-preview, analysis, persistence and
end-to-end completion. Coverage should report analysed files against eligible files, with
exclusions explained.

and proposed future work. Relevant writing or analytical assistance should be disclosed

requirements change. The objective is controlled and observable behaviour under realistic
conditions, not merely a lower duration from one benchmark run.
8.5 Extended Validation and User Studies
The next research stage should use diverse, independently labelled projects and
participants with different levels of security experience.
A user study could measure the time required to locate evidence, the ability to distinguish
suggestions from confirmed results, and the correctness of remediation decisions.
Participant consent and source confidentiality are necessary. These studies would provide
evidence about whether the integrated interface improves review work rather than
relying only on screenshots or developer impressions.
